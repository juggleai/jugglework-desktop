## 1. 文档目的

本文定义 JuggleWork 任务（TODO）功能的产品目标、MVP 范围、页面信息架构、核心交互规则、权限规则、用户故事和验收标准，作为产品、设计、客户端、服务端、测试及运营共同评审的基线。

当前 `add-cloud-tasks` OpenSpec 仅交付云端 Task 核心领域和 Desktop 任务中心，不包含 IM 互操作。本文保留的消息转任务、来源消息、任务卡片、访问申请和任务助手内容仅作为未来独立变更的设计参考，不构成当前 OpenSpec、MVP-A 发布或验收的阻断条件。

- 工期、人员和迭代排期；

## 2. 背景与机会

JuggleWork 已包含组织内 IM 聊天、组织成员、文件、Workspace、Session、Automations 和通知等能力。用户在单聊和群聊中会持续产生行动项，但目前缺少一个独立、持久、可指派、可提醒、可追踪的日常待办系统。

典型问题包括：

1. 聊天中的行动项容易被后续消息淹没；
2. 用户需要切换到外部 TODO 产品记录和跟进事项；
3. “谁负责、何时完成、当前状态”缺少结构化表达；
4. 个人待办、团队任务、聊天上下文和组织成员彼此割裂；
5. JuggleWork 的 Agent 能力虽然可以辅助工作，但不应成为基础任务管理的前置条件。

因此，JuggleWork 需要增加一个面向组织成员日常协作、同时支持私人待办的独立任务应用，并在未来通过独立变更与 IM 深度融合。

## 3. 产品定位

### 3.1 一句话定义

> JuggleWork 任务是一个云端统一、面向组织协作、同时支持私人待办的独立任务应用，并可在未来与 IM 深度融合。

### 3.2 核心价值

> 在任务中心统一记录、管理和协同推进工作，并在未来支持从聊天产生和分享任务。

### 3.3 产品原则

1. **任务是独立产品对象**
   Task 不等于 IM 消息、Session、Agent Todo 或 Automation。

2. **基础体验不依赖 Agent**
   即使没有可用模型、AI Provider 或 Agent，用户仍能完整使用任务功能。

3. **IM 集成独立演进**
   消息转任务、任务卡片和任务助手具有产品价值，但由未来独立 OpenSpec 定义和交付，不阻塞当前核心 Tasks MVP。

4. **云端单一权威**
   私人任务和协作任务均上传云端，不建设本地与云端双主模型。

5. **权限边界清晰**
   Task 权限由服务端独立判断；未来接入来源 IM 消息时，必须分别判断 Task 与消息权限，不能通过任务绕过聊天权限。

6. **低摩擦管理**
   任务可以没有负责人，可以快速创建，核心字段按需补充。

7. **先做日常 TODO，再扩展 Agent 工作流**
   MVP 优先解决记录、指派、提醒、协作和完成闭环。

## 4. 产品目标与非目标

### 4.1 MVP 产品目标

当前 `add-cloud-tasks` MVP 需要实现以下闭环：

```text
手工创建
   ↓
创建私人或协作任务
   ↓
设置 0～N 个负责人、关注人、时间和任务清单
   ↓
负责人在任务中心查看和处理
   ↓
通过活动、通知中心和评论协同
   ↓
完成、重新打开、取消或软删除
```

具体目标：

- 在 JuggleWork 左侧竖向导航栏提供独立“任务”入口；
- 支持个人日常待办和组织内协作任务；
- 支持多人负责、多关注人及无负责人任务；
- 支持开始时间、截止时间、提醒和优先级；
- 支持任务清单、评论、附件、子任务和活动记录；
- 支持云端存储、跨设备读取和云端提醒；
- 保证任务核心能力不依赖 Agent。

从单聊或群聊消息创建任务、将任务发送到 IM、任务助手通知，以及来源消息生命周期处理保留为未来独立变更的目标，不属于当前 MVP-A 范围。

### 4.2 MVP 非目标

以下不进入 MVP：

- 甘特图、时间线、关键路径；
- Portfolio、OKR、项目组合管理；
- 自定义字段；
- 自定义状态工作流；
- 多层级子任务；
- 复杂任务依赖；
- 任务同时属于多个任务清单；
- 完整日历客户端；
- 复杂重复规则；
- 位置提醒；
- 外部访客和公开链接；
- 复杂评论线程和行内评论；
- Agent 自动执行任务；
- Task 与 Session、Agent Todo、Automation 的深度联动；
- Agent 自动创建任务或自动完成任务。

### 4.3 后续演进方向

- **独立 IM 互操作变更**——消息转任务、来源引用与权限、任务卡片、访问申请和任务助手；
- **P1：管理体验增强**——看板、分组、保存视图、重复任务、批量操作、模板、移动端；
- **P2：JuggleWork 差异化**——关联 Session、交给 Agent、关联 Run/Automation、交付物、审批和 Requires attention。

## 5. 目标用户与核心场景

### 5.1 目标用户

| 用户类型 | 主要诉求 |
|---|---|
| 个人用户 | 记录私人待办、安排今日事项、设置提醒 |
| 组织成员 | 接收并完成别人分配的任务，跟进自己负责的事项 |
| 任务创建人 | 从聊天中提取行动项，分配负责人并跟踪结果 |
| 任务关注人 | 不直接负责执行，但需要获得关键进展和完成通知 |
| 任务清单管理员 | 组织团队任务、维护清单成员和任务秩序 |

### 5.2 核心场景

以下涉及 IM 的场景保留为未来独立变更的产品参考；当前 `add-cloud-tasks` 的实现和验收以任务中心内的创建、协作和生命周期为准。

1. 用户在聊天中看到一条行动项，将其转成任务并分配给多人；
2. 用户快速创建一个没有负责人的私人待办，稍后再安排；
3. 用户在“今日”查看今天要处理和已经逾期的事项；
4. 用户在“我负责的”查看组织成员分配给自己的任务；
5. 用户关注某项工作，在状态变化或完成时收到通知；
6. 用户将任务卡片发送到群聊，群成员打开任务协作；
7. 原消息被删除后，用户仍继续处理任务；
8. 用户退出来源群聊后，仍能查看有权限的任务，但不能读取原始消息；
9. 某个任务无人负责，仍然保存在创建人的 Inbox 中；
10. Agent 不可用时，以上流程仍然正常运行。

## 6. 已确认的 P0 产品决策

以下决策已确定，MVP 设计和实现不得与其冲突。

### 6.1 多人负责

- 一个任务支持 0～N 个负责人；
- 创建人不自动成为负责人；
- 任一负责人均可完成整个任务；
- 完成后任务对所有负责人均为已完成；
- 若需要每个人分别完成，应拆分为多个子任务；
- MVP 不支持“每位负责人分别确认后才完成”。

### 6.2 私人任务上传云端

- 私人任务与协作任务均由 Cloud/Server 作为唯一权威数据源；
- 私人任务通过权限隔离，而非本地存储；
- Desktop 可缓存数据，但缓存不是第二写入权威；
- 私人任务可以跨设备访问，并可使用云端提醒。

### 6.3 来源 IM 消息删除（未来独立变更参考）

- 删除或撤回原消息不级联删除任务；
- 任务继续存在并可正常编辑、评论、完成；
- 来源区域显示“原消息已删除或不可访问”；
- 来源快照不得成为恢复已撤回敏感内容的后门。

### 6.4 退出来源群聊（未来独立变更参考）

- 用户退出或被移出来源群聊后，任务依然存在；
- 只要用户仍具备任务权限，就可继续查看和处理任务；
- 用户不能通过任务读取已经无权访问的原消息及群聊上下文；
- 来源区域显示“你已无法访问原始消息”。

### 6.5 允许无负责人任务

- 负责人字段可以为空；
- 无负责人任务进入创建人的 Inbox 和“我创建的”；
- 无负责人任务不进入任何成员的“我负责的”；
- 到期提醒默认发送给创建人；
- 系统可提示“尚未设置负责人”，但不得阻止保存。

### 6.6 核心体验不依赖 Agent

- 任务 CRUD、指派、关注、评论、提醒和权限由确定性服务完成；未来 IM 集成同样不得依赖 Agent；
- Agent 只能作为可选增强能力；
- Agent 不可用时，不影响创建、编辑、完成和协作。

### 6.7 其他 P0 规则

1. **默认可见范围**
   - 手工创建默认为 `private`；
   - 以下 IM 默认规则供未来独立变更使用：从组织聊天创建默认为 `members`；
   - 来源群聊成员不会仅因在群中就自动成为负责人或关注人；
   - 任务共享到群聊后，群聊仅形成任务访问入口，不改变负责人关系。

2. **创建人管理权限**
   - 创建人始终保留任务管理权限；
   - 创建人退出组织后立即失去访问和管理权限；
   - 协作任务继续归组织所有，原创建人以“已离职成员”身份保留在活动记录中；
   - private 任务是“组织内仅创建人可见”，不是脱离组织的个人数据空间；创建人退出组织后进入 30 天冻结期，期间不可被组织其他成员读取，重新加入同一组织可恢复访问，期满按组织数据保留策略清理；
   - 创建人历史身份在活动记录中保留。

3. **删除策略**
   - 负责人可以取消任务，但不能直接删除；
   - 创建人和任务清单管理员可软删除；
   - 软删除任务进入回收状态并保留恢复期；
   - MVP 恢复期确定为 30 天；
   - 恢复期后由服务端异步清理，审计所需的最小事件仍按组织策略保留。

4. **从聊天创建时的默认负责人（未来独立变更参考）**
   - 默认不设置负责人；
   - 消息中明确 @成员时，只给出候选建议，不自动指派；
   - 用户必须在创建弹窗中确认负责人。

5. **重新打开权限**
   - 创建人、任一负责人、任务清单管理员可以重新打开已完成任务；
   - 关注人不能仅凭关注关系重新打开任务。

6. **协作者管理权限**
   - 只有创建人和任务清单管理员可以添加或移除其他负责人、关注人，并扩大任务可见范围；
   - 负责人和关注人可以关注或取消关注自己，但不能借此向第三方授予访问权；
   - 评论中 @无任务访问权限的成员时不自动授权，操作人需请求创建人或清单管理员先共享任务。

7. **创建人退出后的管理兜底**
   - 协作任务若属于任务清单，由该清单管理员接管管理；
   - 不属于任务清单的协作任务由组织 Owner/Admin 获得兜底管理权限，可将一名现有负责人指定为新的创建人；没有负责人时可先添加一名负责人再转移；
   - 该兜底权限只用于防止孤儿任务，不使组织管理员默认读取 private 任务内容。

## 7. 核心概念与对象关系

### 7.1 核心对象

| 对象 | 产品含义 |
|---|---|
| Task | 一条持久的个人或协作待办 |
| Task List | 用于组织一组任务的清单 |
| Assignee | 对任务执行负责的组织成员，可为多人 |
| Follower | 关注任务进展但不承担完成责任的成员 |
| Viewer | 被明确授予只读访问的组织成员，不是负责人或关注人 |
| Subtask | 从属于一个主任务的一层子任务 |
| Comment | 任务内的协作讨论 |
| Attachment | 明确上传或添加到任务的文件 |
| Task Source | 任务的来源；当前支持手工创建，未来可扩展 IM 消息来源 |
| Task Event | 任务字段和协作变化形成的活动记录 |
| Reminder | 面向具体成员的任务提醒 |

### 7.2 对象关系

```text
Organization
  ├── Members
  ├── Task Lists
  │     ├── List Members
  │     └── Tasks
  └── Tasks
        ├── 0..N Assignees
        ├── 0..N Followers
        ├── 0..N Viewers
        ├── 0..N Subtasks（仅一层）
        ├── 0..N Comments
        ├── 0..N Attachments
        ├── 0..N Member Reminders（MVP 每位接收人最多 1 条有效提醒）
        ├── 0..N Events
        └── 0..1 IM Message Source（未来独立变更）
```

### 7.3 Task 与其他 JuggleWork 对象的边界

| 对象 | 与 Task 的关系 |
|---|---|
| IM Message | 未来可以作为任务来源；删除消息不删除任务 |
| Session | MVP 不强绑定，P2 支持关联和从任务启动 Session |
| Agent Todo | 仅是 Agent 一次运行内的临时步骤，不自动同步为 Task |
| Automation | MVP 不关联，P2 作为任务执行策略关联 |
| Notification | 任务事件的一个通知承载渠道，不是任务状态本身 |

## 8. 状态、时间和优先级

### 8.1 任务状态

MVP 状态：

```text
todo → completed
  └→ canceled

completed → todo（重新打开）
canceled  → todo（恢复处理）
```

字段含义：

| 状态 | 中文 | 说明 |
|---|---|---|
| `todo` | 待处理 | 尚未完成的正常任务 |
| `completed` | 已完成 | 已由有权限的成员完成 |
| `canceled` | 已取消 | 不再继续，但保留记录 |

MVP 不引入自定义状态。“进行中”可在 P1 评估，不阻塞 MVP。

### 8.2 时间字段

- 开始时间：可为空；
- 截止时间：可为空；
- 开始时间不得晚于截止时间；
- 时间按用户当前时区展示，服务端保存标准时间和必要的时区信息；
- 修改时间必须记录活动，并按通知策略通知相关成员。

### 8.3 提醒

- 截止时间和提醒时间是两个独立字段；
- MVP 每位提醒接收人对同一任务最多设置 1 条有效提醒；
- 提醒可以设置为具体时间，或在已有截止时间时设置为相对截止时间；
- 截止时间变化时，相对提醒按新截止时间重新计算，绝对提醒保持不变；
- 无负责人时，默认提醒创建人；
- 有负责人时，默认提醒负责人；
- 关注人是否接收提醒由其关注通知设置决定；
- 任务完成、取消、软删除或提醒时间已过后，不再触发该提醒；
- 云端负责提醒调度和多设备去重。

### 8.4 优先级

MVP 支持：

- 无优先级；
- 低；
- 中；
- 高。

## 9. 可见范围与权限模型

### 9.1 可见范围

| 可见范围 | 可访问用户 |
|---|---|
| `private` | 仅创建人 |
| `members` | 创建人、负责人、关注人、被明确授权的 Viewer 及所属任务清单的有权成员 |
| `organization` | 当前组织内所有状态正常的成员只读可见；创建人、负责人和清单管理员按角色获得编辑权限 |

### 9.2 可见范围自动调整

- 手工新建任务默认为 `private`；
- 未来从组织聊天创建任务时默认为 `members`；
- 为私人任务添加其他负责人或关注人时，必须提示并将范围调整为 `members`；
- 用户取消调整时，不添加相关成员；
- “其他成员”指创建人之外的负责人、关注人或清单有权成员；
- 从任务移除最后一个其他成员后，不自动恢复为 `private`，由创建人主动修改；
- private 任务不能加入共享任务清单；用户选择共享清单时，必须确认将任务调整为 `members` 或 `organization`；
- 任务加入清单后，清单成员按清单角色获得任务访问权；移出清单后，由清单带来的访问权立即撤销，但用户通过负责人、关注人等其他关系获得的权限保留；
- 权限冲突时遵循“显式任务成员权限 + 清单成员权限 + organization 范围”的并集；任何服务端明确拒绝和组织失效状态优先于允许。

### 9.3 角色权限矩阵

| 操作 | 创建人 | 负责人 | 关注人 | 清单管理员 | Viewer / 其他只读成员 |
|---|---:|---:|---:|---:|---:|
| 查看任务 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 编辑标题/描述 | ✓ | ✓ | — | ✓ | — |
| 修改开始/截止时间 | ✓ | ✓ | — | ✓ | — |
| 添加/移除负责人 | ✓ | — | — | ✓ | — |
| 添加/移除关注人 | ✓ | 仅关注/取消自己 | 可取消自己 | ✓ | — |
| 完成任务 | ✓ | ✓ | — | ✓ | — |
| 重新打开 | ✓ | ✓ | — | ✓ | — |
| 取消任务 | ✓ | ✓ | — | ✓ | — |
| 评论 | ✓ | ✓ | ✓ | ✓ | — |
| 添加附件 | ✓ | ✓ | — | ✓ | — |
| 软删除 | ✓ | — | — | ✓ | — |

角色可以重叠，权限按允许项取并集；组织成员状态失效或服务端显式拒绝时，拒绝优先。任务软删除后禁止普通内容读取和修改，但原创建人及当前相关清单管理员可以读取最小墓碑信息并执行恢复。移除负责人、取消关注、移出清单或退出组织后，由该关系带来的权限立即失效，客户端在下一次读取或写入时必须重新鉴权。

Viewer 仅有查看权限，不能评论、修改、完成、取消、删除或继续授权他人。创建人和清单管理员可以随时移除 Viewer；被移除后，由 Viewer 关系产生的访问权立即失效。organization 范围下的普通组织成员和清单只读成员遵循同样的只读权限。

### 9.4 状态转换权限

| 转换 | 创建人 | 负责人 | 清单管理员 | 关注人/只读成员 |
|---|---:|---:|---:|---:|
| `todo → completed` | ✓ | ✓ | ✓ | — |
| `todo → canceled` | ✓ | ✓ | ✓ | — |
| `completed → todo` | ✓ | ✓ | ✓ | — |
| `canceled → todo` | ✓ | ✓ | ✓ | — |
| 任意状态 → 软删除 | ✓ | — | ✓ | — |
| 软删除 → 恢复 | ✓ | — | ✓ | — |

### 9.5 Task 权限与来源消息权限（未来独立变更参考）

必须独立校验：

```text
canViewTask(user, task)
canViewMessage(user, conversation, message)
```

- 有 Task 权限不代表有原消息权限；
- 有原消息权限也不代表自动获得 Task 编辑权限；
- Task API 不得因用户能看任务而返回其无权查看的原消息全文、附件或群聊上下文。

## 12. IM 集成需求（未来独立变更参考）

本节保留未来 IM 互操作的产品设计方向，不属于当前 `add-cloud-tasks` OpenSpec，不参与当前 MVP-A 发布验收。具体范围和验收标准必须由后续独立 OpenSpec 重新确认。

### 12.1 从 IM 消息创建任务

单聊和群聊消息菜单增加“创建任务”。

未来变更建议支持以下来源：

- 文本消息；
- 图片消息；
- 文件消息；
- 引用消息。

创建弹窗默认行为：

- 对消息文本去除首尾空白，取第一个非空段落的前 80 个 Unicode 字符作为默认标题，超出时追加省略号；
- 图片消息默认标题为“处理图片”，文件消息默认标题为“处理文件：{文件名}”，引用消息优先使用被引用文本的同一截取规则；
- 原消息作为来源引用；
- 不自动设置负责人；
- 消息中的 @成员可显示为负责人候选，但必须由用户确认；
- 图片和文件不自动复制成任务附件；
- 用户可明确选择“添加为附件”；
- Agent 可选地提供标题建议，但失败时使用确定性截取规则。

### 12.2 重复创建提醒

同一条消息已关联任务时，再次创建应提示：

> 该消息已经关联任务。你可以打开已有任务，或继续创建新任务。

允许一条消息关联多个任务，但系统应避免无提示重复创建。

### 12.3 来源消息展示

来源区域状态：

| 状态 | 展示 | 行为 |
|---|---|---|
| 可访问 | 群名、发送人、时间和安全预览 | 点击跳转原消息 |
| 已删除 | “原消息已删除” | 不可跳转，不返回全文 |
| 无权限 | “你已无法访问原始消息” | 不可跳转，不返回全文 |
| 会话不存在 | “来源会话不可用” | 不可跳转 |

用户提交创建后，用户确认过的任务标题、任务描述和明确添加的附件属于 Task 自有内容，即使来源消息删除也继续保留；消息正文、安全预览、聊天上下文和未明确添加的消息附件属于 IM 来源数据，删除、撤回或失去权限后不得继续返回。

### 12.4 将任务发送到聊天

任务详情提供：

- 发送到聊天；
- 复制任务链接。

发送前必须检查目标会话受众是否都有 Task 权限：

- 若全部有权，发送完整任务卡片；
- 若存在无权成员，创建人或清单管理员可将指定成员加入 Viewer，或将任务调整为 `organization`；普通发送人不能扩大权限；
- 未完成授权时只能发送受限卡片；受限卡片只显示“一个任务被分享”和“申请访问”，不得显示标题、负责人、时间、清单或描述；
- “申请访问”向创建人和清单管理员发送申请；任一管理者批准后，申请人成为 Viewer 并收到结果通知。若任务已无管理者，则由组织 Owner/Admin 处理。

完整任务卡片显示：

- 标题；
- 状态；
- 负责人；
- 截止时间；
- 所属清单；
- 打开任务按钮。

聊天中已发送卡片可以保留发送时快照；用户点击打开时必须重新鉴权并读取最新任务状态。无权限用户始终只能看到受限卡片，不得依赖客户端隐藏字段实现保密。

### 12.5 消息删除与群聊退出

- 删除消息不删除任务；
- 退出群聊不删除任务；
- 用户是否能继续看任务取决于 Task 权限；
- 用户是否能看原消息取决于 IM 权限；
- 不得通过缓存快照绕过撤回、删除和群聊访问控制。

### 12.6 任务助手

JuggleWork IM 中提供系统“任务助手”，负责发送关键任务通知。

未来变更建议支持以下通知：

- 被指派为负责人；
- 被添加为关注人；
- 截止时间由无变有、被移除，或任何日期/时间变化；
- 任务即将到期；
- 任务已逾期；
- 评论中被 @；
- 关注的任务已完成或重新打开；
- 任务被取消。

任务助手卡片至少包含：

- 事件说明；
- 任务标题；
- 负责人；
- 截止时间；
- 打开任务按钮；
- 对允许的场景提供“标记完成”等快捷操作。

- 搜索结果只能包含用户有权访问的任务；
- 私人任务不得进入其他组织成员搜索结果；
- 未来接入 IM 来源时，来源消息全文不应被 Task 搜索索引自动扩展。

### 14.2 筛选组合

- 同一字段内多选为 OR；
- 不同字段之间为 AND；
- 用户可以一键清除筛选；
- 当前筛选数量在工具栏显示；
- MVP 不保存自定义筛选视图，P1 支持。

### 14.3 分页

列表和活动均需支持服务端分页或游标加载，不能依赖客户端一次拉取组织全部任务。

### 14.4 幂等、并发和断网行为

- 创建任务、添加负责人、评论、完成和提醒变更等写操作必须携带幂等标识；用户重试不得产生重复任务或重复关系；
- 编辑基于任务版本号进行乐观并发控制；版本冲突时不得静默覆盖，客户端保留用户未提交内容，提示“任务已被更新”，并提供“查看最新内容”和“重新应用修改”；
- MVP 不承诺离线创建或离线编辑；断网时写操作不可提交，恢复网络后由用户重新确认；
- 当前进程可显示已经加载的数据，但登出、切换组织或成员权限被撤销后必须立即清理对应缓存；
- 重新联网后，客户端必须重新获取权限和任务版本，不能用旧缓存绕过服务端拒绝。

## 15. 评论、附件和子任务

### 15.1 评论

- 有评论权限的成员可发表评论；
- 支持 @组织成员；
- @成员必须已经有任务访问权限；
- @无权限成员时阻止提交该提及，并提示联系创建人或清单管理员先共享任务；
- 支持编辑和软删除自己的评论；
- 评论写入活动记录；
- MVP 不做多层评论线程。

### 15.2 附件

- 用户明确上传的文件成为任务附件；
- 附件访问权限服从任务权限和文件自身权限；
- 无权访问文件时显示不可访问状态，不泄露文件内容。

未来接入 IM 来源时，来源消息中的文件不自动成为附件；用户明确添加后才成为任务附件，且删除来源消息不自动删除已明确添加的附件。

### 15.3 子任务

- MVP 只支持一层子任务；
- 子任务是独立可完成对象；
- 子任务可设置负责人和截止时间；
- 主任务完成时，如仍有未完成子任务，弹出确认提示；
- 完成全部子任务不自动完成主任务；
- MVP 不支持子任务继续创建下级子任务。

## 16. 删除、取消、归档与恢复

### 16.1 取消任务

- 用于表示任务不再需要处理；
- 任务仍可搜索和查看；
- 任务活动记录保留；
- 有权限成员可以恢复为待处理。

### 16.2 软删除任务

- 仅创建人和任务清单管理员可执行；
- 删除前需要确认；
- 删除后不在普通列表和搜索结果中展示；
- 在 30 天恢复期内，仅原创建人或当前相关任务清单管理员可以从“回收站”恢复；
- 软删除后，负责人和关注人无法通过普通深链查看内容；
- 恢复后保留原任务 ID、成员关系和活动记录；
- 未来接入 IM 互操作时，来源消息和聊天卡片不随任务物理删除，但打开时显示任务不可用或已删除。

### 16.3 归档任务清单

- 归档清单不等于删除任务；
- 清单内任务继续存在；
- 清单从默认导航隐藏；
- 用户可在归档清单入口恢复。

## 17. MVP 用户故事与验收标准

以下使用 `US-模块-编号` 标识，优先级均为 P0，除非特别注明。

### 17.1 导航与任务中心

#### US-NAV-01：打开独立任务应用

**作为** JuggleWork 用户，
**我希望** 从左侧竖向导航栏进入任务，
**以便** 独立管理日常待办。

**验收标准：**

1. Given 用户已登录并进入 JuggleWork，When 查看左侧竖向导航，Then 可看到“任务”独立入口；
2. When 点击“任务”，Then 打开 `/tasks` 对应的任务应用；
3. Then 任务应用显示二级导航和主内容区；
4. Given Agent 或 AI Provider 不可用，When 打开任务，Then 任务应用仍可正常使用；
5. When 用户离开后再次进入任务，Then 默认恢复上次访问的任务视图；
6. When 存在需用户处理的未读任务事件，Then 任务入口可以显示角标。

#### US-NAV-02：浏览系统视图

**作为** 用户，
**我希望** 按今日、我负责的、我创建的和我关注的查看任务，
**以便** 快速定位当前工作。

**验收标准：**

1. 二级导航至少包含今日、收集箱、我负责的、我创建的、我关注的、活动、全部任务、已完成、回收站和归档清单入口；
2. “我负责的”仅显示当前用户是负责人的任务；
3. “我创建的”包含当前用户创建的无负责人任务；
4. “我关注的”仅显示当前用户为关注人的任务；
5. “已完成”默认显示已完成任务，不混入待处理任务；
6. 各视图查询结果均服从任务访问权限。

#### US-NAV-03：查看收集箱和今日

**作为** 用户，
**我希望** 查看尚未归类的任务和今天需要处理的任务，
**以便** 完成每日整理和执行。

**验收标准：**

1. 收集箱仅显示当前用户创建、状态为 `todo` 且未归入任务清单的任务；
2. 收集箱包含无负责人任务；
3. 今日按当前用户时区计算；
4. 今日包含今天开始、今天截止和已逾期的 `todo` 任务；
5. 已完成、已取消和软删除任务不进入今日；
6. 今日默认先显示逾期任务，再按截止时间升序显示。

### 17.2 创建和编辑任务

#### US-TASK-01：快速创建私人任务

**作为** 用户，
**我希望** 只输入标题即可创建私人任务，
**以便** 快速记录待办。

**验收标准：**

1. Given 用户在任务中心，When 输入非空标题并提交，Then 创建成功；
2. Then 默认可见范围为 `private`；
3. Then 默认负责人为空；
4. Then 任务出现在创建人的 Inbox/我创建的和全部任务中；
5. Then 不出现在任何用户的“我负责的”中；
6. Given 标题为空，When 提交，Then 阻止创建并显示校验提示；
7. Given Agent 不可用，When 创建，Then 创建仍成功。

#### US-TASK-02：创建无负责人任务

**作为** 用户，
**我希望** 在未确定负责人时保存任务，
**以便** 先记录再安排。

**验收标准：**

1. 负责人为空时允许保存；
2. UI 可以显示“未设置负责人”，但不能作为错误；
3. 无负责人任务的到期提醒默认发送给创建人；
4. 后续可以添加一个或多个负责人；
5. 添加负责人后任务进入对应成员的“我负责的”。

#### US-TASK-03：设置多人负责

**作为** 任务创建人或清单管理员，
**我希望** 为一个任务设置多个负责人，
**以便** 让多位成员共同推进同一事项。

**验收标准：**

1. 创建人或清单管理员可从组织成员目录选择 0～N 个负责人；
2. 同一成员不可重复添加；
3. 添加负责人后，所有负责人均可在“我负责的”中看到任务；
4. 添加负责人写入活动记录；
5. 新负责人收到指派通知；
6. private 任务添加其他成员时，系统提示将可见范围调整为 `members`；
7. 用户取消调整时，不添加负责人。

#### US-TASK-04：任一负责人完成多人任务

**作为** 任务负责人，
**我希望** 完成整个任务，
**以便** 明确任务已经结束。

**验收标准：**

1. 任一负责人均可完成任务；
2. 多负责人任务完成前提示“将对所有负责人标记为已完成”；
3. 确认后任务状态统一变为 `completed`；
4. 其他负责人、创建人和关注人按通知策略收到完成通知；
5. 任务从所有负责人的默认未完成视图移除；
6. 活动记录包含完成人和完成时间；
7. 不记录每位负责人独立完成状态。

#### US-TASK-05：重新打开任务

**作为** 创建人、负责人或清单管理员，
**我希望** 重新打开已完成任务，
**以便** 在工作尚未真正结束时继续处理。

**验收标准：**

1. 创建人、任一负责人和清单管理员可重新打开；
2. 仅关注人不能重新打开；
3. 重新打开后状态变为 `todo`；
4. 任务重新进入相关负责人的未完成视图；
5. 活动记录包含操作人和时间；
6. 相关成员按通知策略收到通知。

#### US-TASK-06：设置时间和提醒

**作为** 用户，
**我希望** 设置开始时间、截止时间和提醒，
**以便** 安排和按时处理任务。

**验收标准：**

1. 开始时间、截止时间均可为空；
2. 开始时间晚于截止时间时阻止保存并提示；
3. 提醒时间可以独立于截止时间设置；
4. 每位接收人对同一任务最多存在 1 条有效提醒；
5. 时间按当前用户时区正确展示；
6. 无负责人时提醒默认投递给创建人；
7. 有负责人时提醒默认投递给负责人；
8. 相对提醒只可在存在截止时间时设置，截止时间变化后按新时间重算；
9. 同一提醒在多个设备上不得重复形成多个业务事件。

### 17.3 列表、筛选和搜索

#### US-LIST-01：列表查看与行内操作

**作为** 用户，
**我希望** 在列表中快速查看和更新任务，
**以便** 减少进入详情页的操作。

**验收标准：**

1. 列表显示完成状态、标题、负责人、开始时间和截止时间；
2. 用户可以行内完成任务；
3. 有权限用户可以行内设置负责人和时间；
4. 点击标题打开任务详情；
5. 无权限字段显示为只读；
6. 分页加载时不重复、不丢失任务。

#### US-LIST-02：筛选和排序

**作为** 用户，
**我希望** 按成员、状态、时间和优先级筛选排序，
**以便** 聚焦需要处理的任务。

**验收标准：**

1. 支持按负责人、创建人、关注人、状态、截止时间、优先级和任务清单筛选；
2. 同字段多选按 OR，不同字段按 AND；
3. 显示当前生效的筛选数量；
4. 支持一键清除筛选；
5. 支持按截止时间、创建时间、更新时间和优先级排序；
6. 切换筛选和排序不得返回无权限任务。

#### US-LIST-03：搜索任务

**作为** 用户，
**我希望** 搜索有权限的任务，
**以便** 快速找到历史或当前事项。

**验收标准：**

1. 支持搜索标题和描述；
2. 可通过负责人、创建人显示名命中相关任务；
3. private 任务不会出现在其他成员搜索结果中；
4. 搜索无结果时显示明确空状态。

未来接入 IM 来源时，无权访问的来源消息内容不得参与结果展示。

### 17.4 任务清单

#### US-LISTSET-01：创建任务清单

**作为** 用户，
**我希望** 创建任务清单，
**以便** 按项目或业务组织任务。

**验收标准：**

1. 用户可以设置清单名称、说明、颜色或图标；
2. 名称必填；
3. 可以设置 private、members 或 organization 可见范围；
4. 创建人自动成为清单管理员；
5. 清单出现在任务二级导航；
6. 清单可归档并从默认导航隐藏。

#### 任务清单权限规则

- private 清单仅创建人可见和管理；
- members 清单的管理员可以管理清单和成员，普通成员可以查看并按任务角色编辑任务；
- organization 清单对组织内状态正常成员可见，只有管理员可管理清单成员和配置；
- 清单成员角色变化不改变任务的创建人、负责人或关注人关系；
- 清单管理员只能管理当前仍属于该清单的任务；任务移出后，管理员由清单获得的管理权限立即失效。

#### US-LISTSET-02：将任务加入清单

**作为** 用户，
**我希望** 将任务放入一个任务清单，
**以便** 统一组织和查看。

**验收标准：**

1. 一个任务在 MVP 中最多属于一个清单；
2. 从一个清单移动到另一个清单时，原归属被替换；
3. 移动操作写入活动记录；
4. private 任务移入共享清单时必须提示提升为 `members` 或 `organization`；其他情况下访问权按任务显式成员、Viewer、清单成员和 organization 范围取并集；
5. 归档清单不删除其中任务。

#### US-LISTSET-03：管理和归档任务清单

**作为** 清单管理员，
**我希望** 管理清单成员并归档不再活跃的清单，
**以便** 维护团队任务空间。

**验收标准：**

1. 管理员可以重命名清单、编辑说明、颜色或图标；
2. 管理员可以添加或移除清单成员，并设置管理员或成员角色；
3. 成员被移除后，由清单关系产生的任务访问权立即失效；
4. 管理员可以归档清单，归档后清单从默认导航隐藏；
5. 归档清单中的任务不被删除；
6. 管理员可以从“归档清单”恢复清单；
7. private 任务加入共享清单前必须确认提升可见范围。

### 17.5 IM 消息转任务（未来独立变更参考）

本节用户故事不属于当前 `add-cloud-tasks` 的验收范围，也不阻塞 MVP-A；后续独立 OpenSpec 可复用并重新确认这些故事。

#### US-IM-01：从文本消息创建任务

**作为** IM 用户，
**我希望** 将聊天消息转为任务，
**以便** 不遗漏聊天中的行动项。

**验收标准：**

1. 单聊和群聊文本消息菜单包含“创建任务”；
2. 点击后打开创建任务弹窗；
3. 默认标题由确定性规则从消息文本截取；
4. 默认负责人为空；
5. 消息中的 @成员只作为候选建议；
6. 用户确认提交后创建任务并保存来源引用；
7. 新任务默认可见范围为 `members`；
8. Agent 失败或未配置时不影响创建。

#### US-IM-02：从图片或文件消息创建任务

**作为** IM 用户，
**我希望** 从图片或文件消息创建任务，
**以便** 对相关内容安排后续处理。

**验收标准：**

1. 图片和文件消息菜单包含“创建任务”；
2. 创建弹窗显示来源类型和安全预览；
3. 图片或文件不自动复制为任务附件；
4. 用户可明确选择添加为附件；
5. 没有可用文本时使用确定性占位标题，并要求用户确认或编辑；
6. 创建后来源消息与任务建立关联。

#### US-IM-03：避免无提示重复创建

**作为** 用户，
**我希望** 在消息已有任务时收到提示，
**以便** 避免误建重复任务。

**验收标准：**

1. 同一消息已有一个或多个关联任务时，再次创建显示提示；
2. 用户可以打开已有任务；
3. 用户可以明确选择继续创建新任务；
4. 系统不得强制一条消息只能关联一个任务。

#### US-IM-04：原消息删除后继续使用任务

**作为** 任务成员，
**我希望** 原消息删除后任务仍然存在，
**以便** 已形成的工作不受聊天清理影响。

**验收标准：**

1. 删除或撤回原消息不改变任务状态；
2. 任务标题、描述、成员、评论和附件继续存在；
3. 来源区域显示“原消息已删除或不可访问”；
4. 点击来源不返回原消息全文；
5. 任务不能通过来源快照恢复已经撤回的敏感内容；
6. 删除消息不触发任务删除或取消。

#### US-IM-05：退出群聊后继续使用任务

**作为** 已退出来源群聊的任务成员，
**我希望** 继续处理有权限的任务，
**以便** 任务协作不因群成员关系变化而中断。

**验收标准：**

1. 退出或被移出来源群聊不删除任务；
2. 用户仍有 Task 权限时可以打开任务；
3. 用户无原消息权限时，来源区域显示“你已无法访问原始消息”；
4. 点击来源不得打开群聊或返回消息上下文；
5. 若用户同时失去 Task 权限，则不能继续查看任务；
6. Task 权限和 IM 权限由服务端分别校验。

#### US-IM-06：发送任务卡片到聊天

**作为** 任务成员，
**我希望** 将任务发送到聊天，
**以便** 在会话中同步和推进任务。

**验收标准：**

1. 任务详情提供“发送到聊天”；
2. 用户可选择有权发送消息的单聊或群聊；
3. 目标会话所有成员均有 Task 权限时，完整卡片显示标题、状态、负责人、截止时间和打开按钮；
4. 目标会话存在无权成员且未扩展授权时，只发送不含任务字段的受限卡片；
5. 卡片打开时重新鉴权并读取最新任务状态；
6. 无权查看任务的成员不得在卡片正文或点击结果中看到标题、负责人、截止时间、清单和描述；
7. 发送任务卡片不自动将群成员设为负责人或关注人。

### 17.6 关注、评论和活动

#### US-COLLAB-01：关注任务

**作为** 用户，
**我希望** 关注某个任务，
**以便** 在不承担负责人角色时获得进展。

**验收标准：**

1. 有权限用户可关注或取消关注任务；
2. 关注后任务进入“我关注的”；
3. 关注人按策略收到评论、完成和重新打开通知；
4. 关注人不能仅凭关注关系完成、重新打开或删除任务；
5. 关注变化写入活动记录。

#### US-COLLAB-02：发表评论和 @成员

**作为** 任务成员，
**我希望** 评论并 @相关成员，
**以便** 围绕任务协作。

**验收标准：**

1. 有评论权限的成员可以发表评论；
2. 支持 @有任务访问权限的组织成员；
3. @无任务权限的成员时，阻止该提及并提示先联系创建人或清单管理员共享任务；
4. 被 @成员收到通知；
5. 评论显示作者和时间；
6. 评论的创建、编辑和删除服从权限并留下必要活动记录。

#### US-COLLAB-03：查看活动记录

**作为** 任务成员，
**我希望** 查看任务变化历史，
**以便** 了解谁在何时做了什么。

**验收标准：**

1. 活动至少记录创建、指派、取消指派、时间变化、状态变化、清单变化和评论；
2. 活动显示操作者和时间；
3. 无法访问的敏感内容不出现在活动中；
4. 活动按时间排序并支持分页；
5. 活动记录不可由普通用户直接修改。

### 17.7 通知

#### US-NOTIFY-01：收到任务指派通知

**作为** 被指派成员，
**我希望** 收到任务通知，
**以便** 及时发现新任务。

**验收标准：**

1. 新增负责人后生成一条稳定业务事件；
2. 事件出现在任务活动页和全局通知中心；
3. 通知包含任务标题、截止时间和打开按钮；
4. 多渠道投递不产生多个重复业务事件；
5. 点击通知打开对应任务。

通过 IM 任务助手发送同一通知属于未来独立变更，不阻塞本用户故事的当前验收。

#### US-NOTIFY-02：收到到期和逾期提醒

**作为** 任务负责人或无负责人任务的创建人，
**我希望** 收到到期提醒，
**以便** 按时完成任务。

**验收标准：**

1. 云端在设定时间触发提醒；
2. 无负责人任务提醒创建人；
3. 有负责人任务提醒负责人；
4. 已完成、已取消或已删除任务不再发送未来提醒；
5. 修改提醒后旧计划失效；
6. 多设备不会重复创建业务提醒；
7. 逾期状态根据截止时间和任务状态正确计算。

### 17.8 附件和子任务（MVP-B）

#### US-CONTENT-01：管理任务附件

**作为** 有编辑权限的任务成员，
**我希望** 添加和移除任务附件，
**以便** 将执行所需资料集中到任务中。

**验收标准：**

1. 用户可以明确上传文件作为附件；
2. 只有上传者、创建人和清单管理员可以移除附件；
3. 用户同时满足 Task 和文件访问权限时才能下载或预览；
4. 无文件权限时只显示“附件不可访问”，不显示受保护的预览和内容。

未来接入 IM 来源时，来源文件不会仅因创建任务而自动成为附件；用户可以明确添加，并且来源消息删除不删除已经明确添加的任务附件。

#### US-CONTENT-02：创建一层子任务

**作为** 有编辑权限的任务成员，
**我希望** 将任务拆成一层子任务，
**以便** 分别安排具体步骤。

**验收标准：**

1. 主任务可以创建多个子任务；
2. 子任务可设置负责人、截止时间并独立完成；
3. 子任务不能继续创建下级子任务；
4. 全部子任务完成不自动完成主任务；
5. 主任务存在未完成子任务时，完成主任务必须二次确认；
6. 删除主任务时，子任务随主任务进入同一软删除状态并可一并恢复。

### 17.9 删除和恢复

#### US-DELETE-01：取消任务

**作为** 有编辑权限的任务成员，
**我希望** 取消不再需要的任务，
**以便** 保留记录但停止跟进。

**验收标准：**

1. 创建人、负责人和清单管理员可取消任务；
2. 取消后状态为 `canceled`；
3. 取消任务不出现在默认未完成视图；
4. 活动记录包含操作人和时间；
5. 创建人、任一负责人或清单管理员可以恢复为 `todo`；
6. 未来提醒被取消。

#### US-DELETE-02：软删除并恢复任务

**作为** 创建人或清单管理员，
**我希望** 删除误建任务并在恢复期内恢复，
**以便** 安全管理任务数据。

**验收标准：**

1. 仅创建人和清单管理员可软删除；
2. 删除前显示确认；
3. 删除后任务不出现在普通列表、搜索和提醒中；
4. 30 天恢复期内，仅原创建人或当前相关任务清单管理员可以恢复；
5. 恢复后任务 ID、成员、评论和活动保持不变；
6. 恢复期满后的处理遵循组织数据保留策略。

### 17.10 Agent 独立性

#### US-CORE-01：无 Agent 条件下完整使用任务

**作为** 未配置 AI Provider 或 Agent 暂时不可用的用户，
**我希望** 正常使用任务，
**以便** 日常待办不依赖 AI 服务。

**验收标准：**

1. 可以打开任务应用；
2. 可以创建、编辑、完成和重新打开任务；
3. 可以添加负责人、关注人、评论和附件；
4. 可以收到云端提醒和任务通知；
5. Agent 相关失败不回滚已经成功的基础任务操作；
6. UI 不应要求用户先配置模型才能使用任务。

## 18. MVP 发布验收总表

以下 18.1～18.4 为当前核心 Tasks MVP（MVP-A + MVP-B）验收总表；MVP-A 可以先作为首发版本上线，但必须满足 18.5 中的 MVP-A 首发阻断范围及其中涉及的全部安全、数据和体验要求。附件和子任务仅在 MVP-B 上线时成为阻断项。IM 消息转任务、来源消息、任务卡片、访问申请和任务助手由未来独立 OpenSpec 验收，不属于本表或当前 MVP-A/MVP-B 的阻断范围。

### 18.1 功能完整性

- [ ] 左侧竖向导航存在独立任务入口；
- [ ] 系统视图查询准确；
- [ ] 支持 0～N 个负责人；
- [ ] 支持关注人；
- [ ] 支持私人和协作任务；
- [ ] 支持开始、截止和提醒；
- [ ] 支持任务清单；
- [ ] 支持评论、附件和一层子任务；
- [ ] 支持取消、软删除和恢复；
- [ ] Agent 不可用时核心流程可用。

### 18.2 权限与安全

- [ ] private 任务不会被其他成员搜索或读取；
- [ ] 多人任务成员权限准确；
- [ ] 附件访问同时遵守任务和文件权限；
- [ ] 所有修改操作均校验组织和成员身份。

### 18.3 数据与可靠性

- [ ] Cloud/Server 是唯一权威；
- [ ] 客户端重试不会重复创建任务或重复指派；
- [ ] 列表和活动支持分页；
- [ ] 并发编辑具备版本冲突处理；
- [ ] 提醒修改和任务完成后旧提醒不会继续投递；
- [ ] 多渠道通知使用稳定事件去重；
- [ ] 软删除和恢复保持任务身份及关联数据；

### 18.4 体验

- [ ] 只输入标题即可完成创建；
- [ ] 无负责人可以保存；
- [ ] 多人任务完成前有明确提示；
- [ ] 主要视图均有加载、空、错误和无权限状态；
- [ ] 常用列表操作无需进入完整详情页；
- [ ] 任务入口角标、活动未读和全局通知状态一致。

### 18.5 MVP 分阶段交付

为控制首版范围，当前核心 Tasks MVP 分为两个连续的小版本；两者均遵守本 PRD 的权限和数据模型。IM 互操作不属于这两个版本，由未来独立变更交付。

#### MVP-A：首发阻断范围

- 独立任务入口和系统视图；
- Task CRUD、多人负责、关注、无负责人和三种可见范围；
- 开始时间、截止时间、单成员单提醒；
- 基础评论；
- 任务清单基础归类；
- 活动事件和通知中心关键通知；
- 搜索、基础筛选和截止时间排序；
- 取消、软删除、回收站和 30 天恢复；
- Cloud/Server 单一权威和无 Agent 完整可用。

#### MVP-B：首发后同一 MVP 周期

- 附件；
- 一层子任务；
- 清单成员角色管理、归档清单；
- 字段显示配置和更多排序；
- 更完整的通知偏好和系统通知；
- 批量已读和活动页体验完善。

MVP-A 未满足不得以 MVP 完成名义上线；MVP-B 可以在不改变核心模型和交互原则的前提下随后的增量版本交付。未实现 IM 转换、来源引用、任务卡片或任务助手不影响当前 MVP-A/MVP-B 的完成判定。

## 20. 成功标准

当前核心 Tasks MVP 发布后，应重点验证以下产品假设：

1. 用户愿意在 JuggleWork 内记录日常待办，而不是切换到外部工具；
2. 负责人能够通过“我负责的”和提醒及时处理任务；
3. 创建人和关注人能够通过活动和通知跟进进度；
4. 私人任务与组织协作任务可以在同一任务中心内安全共存；
5. 即使不使用 Agent，任务产品仍能形成独立价值和使用习惯。

“IM 消息转任务是否为高频创建入口”保留为未来 IM 互操作变更上线后的产品假设。

建议在灰度阶段设置基线目标，具体数值由现有活跃用户量和 IM 使用数据确定。

## 21. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Task 与 Session/Agent Task 术语冲突 | 产品和代码语义混乱 | 产品统一称“任务”，内部领域建议使用 `ProductTask` 或 `UserTask` |
| 私人任务权限泄露 | 高安全风险 | 服务端强制组织与成员授权，搜索和通知同样校验 |
| 来源消息快照泄露撤回内容 | 违反用户预期 | 仅保留受限预览，删除/无权限后不返回敏感原文 |
| 多负责人完成语义不清 | 误操作 | 完成前明确提示整体完成；分别完成使用子任务 |
| 通知过多 | 用户关闭通知 | 只对关键事件主动通知，普通修改仅进活动记录 |
| 群聊分享和 Task 权限不一致 | 卡片无法打开或泄露 | 打开时实时鉴权，发送前提示受众范围 |
| 云端网络中断 | 无法实时编辑 | 显示缓存和明确离线状态；写入策略由技术设计定义 |
| IM 与任务数据强耦合 | 删除消息影响任务 | 生命周期独立，以引用关系连接 |
| Agent 被误认为基础依赖 | 无模型用户无法使用 | 基础流程全部提供确定性实现并单独验收 |

## 22. 评审重点

第 6 节所列核心 Tasks P0 决策已经确认，本轮不重新打开。IM 相关决策作为未来独立变更参考，不参与当前实现评审。当前评审重点是检查核心决策是否被页面、权限、用户故事和验收标准完整承接，并确认以下实现范围：

1. 产品定位是否明确聚焦“组织日常协作 TODO”；
2. 左侧一级任务入口及三栏信息架构是否成立；
3. MVP 范围是否足以形成从任务创建到完成的核心闭环；
4. 多负责人整体完成规则是否在所有入口中表达一致；
5. private、members、organization 三种可见范围是否在 UI 中清晰表达；
6. 无负责人、组织切换、并发冲突等既定边界是否具有完整测试覆盖；
7. 通知策略是否足够及时且不会造成过度打扰；
8. MVP-A 与 MVP-B 的交付边界是否可执行；
9. PRD 通过后 UI 原型需要优先覆盖哪些关键路径。

## 24. 结论

JuggleWork Tasks 的当前 MVP 是一个独立的云端任务应用，面向组织内日常待办和协作，重点打通：

```text
手工创建任务
   ↓
多人负责 / 关注 / 时间 / 提醒 / 清单
   ↓
任务中心统一管理
   ↓
评论、活动和通知中心协作
   ↓
完成、重新打开、取消或恢复
```

该产品在 MVP 阶段不依赖 Agent。Agent、Session、Automation、审批和交付物将在后续阶段作为 JuggleWork 的差异化增强能力接入，但不得改变 Task 作为独立、稳定、可协作待办对象的基本定位。IM 消息转任务、来源消息、任务卡片、访问申请和任务助手同样作为未来独立变更接入，不阻塞当前 `add-cloud-tasks` 的实现、验收或发布。
