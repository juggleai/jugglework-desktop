  - **Known gap, honestly not closed**: no proactive refresh before a minted agent token's `expiresAt`. The push effect re-mints on the next sign-in/account-switch/Den-session-change, same as the session token's own refresh story — but if a poll cycle outlives a token's lifetime with no such event in between, `listPendingDeliveries`/`claimDelivery` will start failing until the next push. A `scheduleTokenRefresh`-style timer (remote control's own agent already has one, `remote-control-agent.mjs`) is the natural fix but wasn't built this pass — out of proportion with "wire up resolveAuth."
  - **Gap found and closed this pass, discovered by trying to actually run the loop end-to-end**: a real live test — replaying a `pull_request` webhook through jugglework-server's dev-replay endpoint against a real bound repository (`juggleai/skillhub`) with a real, saved, enabled event-triggered automation subscribed to exactly that event type — returned `enqueuedCount: 0` every time. Root cause: `PUT /automations/:automationId/event-subscription` (jugglework-server's `AutomationEventSubscriptionInput`-backed endpoint, fully built and tested on that side) was never called from anywhere in this repo. Every prior pass built the *consumption* side of the pipeline (parse/poll/auth) on the assumption that a server-side subscription already existed, but nothing ever created one — a locally "enabled" event-triggered automation was, from the server's perspective, indistinguishable from one that doesn't exist. Fixed with `subscription-sync.ts` (`AutomationSubscriptionSync`), a self-driven periodic reconciler matching `event-poller.ts`'s own established pattern (not a push-on-every-mutation-route approach, which would mean auditing every automation write route for a missed call site): each cycle it re-reads every local automation definition, computes the desired server-side subscription state (`desiredGithubEventSubscription` — event types, branch/label filters unioned across all `matches`, `enabled` true for `lifecycle` `enabled`/`shadow`, false for `paused`/`completed`, absent entirely for non-event triggers or soft-deleted automations), diffs against an in-memory "last successfully pushed" digest, and only calls `upsertEventSubscription`/`deleteEventSubscription` (new `github-event-client.ts` methods, `requireAgentToken: true` — this endpoint needs the same device agent token as polling) when something actually changed. One automation's push failure doesn't block others in the same cycle and is retried the next cycle. 8 tests (`subscription-sync.test.ts`) cover the field mapping, no-op-when-unchanged, re-push-on-change, delete-only-when-previously-synced, and failure-isolation behavior. Wired into `server.ts`'s startup/shutdown alongside the poller and scheduler. **Live-verified this pass**: after rebuilding and restarting the real desktop app with this fix, the reconciler correctly *attempted* the push and failed with the exact same `github_event_relay_agent_unavailable` this test machine's polling already fails with (confirmed via `GET /automations/:id/event-subscription` returning 404 and the sync's own failure log) — i.e. the fix is reached and behaves correctly; the one remaining blocker on this specific machine is the device-agent-token precondition already described above (task 3.1's second bullet), not a new gap.

  **Out of scope entirely this pass**: the primary IM-push delivery channel — `apps/server` has no persistent JuggleIM connection of its own (the existing one lives in the renderer, for chat), so headless IM delivery needs its own dedicated connection there, distinct from and larger than the polling fallback built this pass.
