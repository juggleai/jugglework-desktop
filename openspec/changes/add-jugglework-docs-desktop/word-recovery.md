# Word 绑定建立、检查点和重开恢复

本文维护 Word 与原生 AFFiNE 会话的关联恢复契约。只保存账号／文件／页面关联不能证明内容仍一致。稳定对象映射、恢复原生变化与远端回写仍属于真实 SDK PoC 门槛，不新增 DOCX 合并算法或离线补丁日志。

## 1. 本地检查点

cloud-doc-bindings.json 中 schemaVersion 初值改为 2，增加 checkpoint 可空对象。旧关联无检查点时保持 paused，不猜测建立新基线。检查点字段如下：

| 字段 | 类型／含义 |
| --- | --- |
| checkpointId | UUID，不可变检查点身份 |
| localSavedFileSha256 | 64 位小写十六进制，最近双方确认一致且 Office 保存成功的真实文件摘要 |
| nativeStateVector | 原生 Yjs 状态向量 base64，用于恢复定位；不是内容相等或已落库证明 |
| nativeSnapshotRef | 本机原生 Y.Doc 检查点资源引用，保留原生编码，不存远程任意路径 |
| mappingCheckpointRef | SDK 稳定对象与原生对象／相对位置映射资源引用，必须由真实 PoC 证明可重开复用或重建 |
| mappingVersion / nativeSchemaVersion | 已验证映射与锁定 schema 版本 |
| confirmedAt | UTC 毫秒整数；双方当前模型对应及本地落盘成功的确认时间 |

nativeSnapshotRef 使用当前原生 IndexedDB／本地既有持久化边界，归属源账号＋租户＋页面＋binding，不能只用 pageId 混用其他账号缓存。映射检查点只存定位关联与必要校验信息，不另建第三种正文树。状态向量本身无法证明删除集合、Word 内容或文件相等，恢复必须读取实际原生检查点。

不可变检查点资源先写完，再用既有原子写文件／rename 模式更新关联指针；失败沿用上个完整检查点，孤立旧资源可后续清理。只保留当前及上一份完整检查点，不维护无限历史。无本地数据库、锁服务或自定义变更日志。

检查点只在以下条件同时成立时推进：没有未决或 unknown 桥操作，远端变化已回写当前 SDK，映射有效，本地 Office 保存明确成功，文件摘要对应这次保存；原生观察状态与 Word 对应模型在捕获期间未再变化。有变化则本轮不推进并稍后重试，不阻塞其他原生协作者，不引入跨编辑器锁。保存成功不等于服务器已备份，状态文案继续分开。

当前源码已实现上述写入边界：AFFiNE `editor.checkpoint` 返回原生 Y.Doc update、状态向量和 Yjs 字符相对位置映射；Desk 在 Office 保存前准备、保存后再次读取 Word revision 与原生状态向量，完全一致才提交。Office Server 的 `savedFileSha256` 来自真实落盘文件。检查点目录先完整写入后 rename，随后更新 `cloud-doc-bindings.json` 指针；指针成功后才删除第三旧资源。首次关联必须同步形成首个检查点，失败不保留 active。

## 2. 首次建立关联

新 DOCX 转云页面后，先验证转换结果及支持对象、构建稳定映射，再形成双方确认一致的首个检查点，最后将关联设为 linked。转换成功不自动建立可写绑定。

选择已有云页面时不能把两份任意内容直接连起来。只有可证明是同一检查点对应内容且映射成立时才恢复；否则显示“这份文件与云文档尚未建立共同版本”，保留双方内容，提供打开云文档、断开并另存／导入新副本。不得为了建关联整页覆盖既有页面、评论或历史。

## 3. 重开握手

1. 固定源账号、租户、pageId 和文件身份，完成新登录交接、源授权与原生 Doc 写权限检查。
2. 在现有 Office admission 安全边界读取当前活跃模型和真实文件摘要。摘要用于保存证明和文件身份，不单独作为正文分叉判断。由不可变原生快照核对当前模型的有序段落 ID、文本、段落类型、加粗和斜体，包含空段落和 UTF-16 字符；即使文件摘要相同，也不能跳过模型核对。核对检查点完整性、版本及账号分区；先不发任何 Word → Docs 写入。
3. 载入同一原生 Y.Doc 检查点及原生缓存，通过 Provider 正常握手／状态向量恢复云端变化；服务端每次恢复更新仍做当前授权。只在原生状态和可恢复映射均明确后允许回写 SDK。
4. 原生变化定点回写同一 SDK，完成原保存及新的共同检查点后，开放双向编辑。不能把初始化全量文档当作新增正文再次提交。

当前源码按以上顺序实现自动恢复：进程启动先暂停旧 active；Word 重开后由当前账号／组织申请新 editor grant，主进程精确匹配本地工作区和相对路径并确认真实 SHA-256 可用；AFFiNE `editor.restore` 验证不可变 Y.Doc 快照、状态向量和字符映射，核对实际 Word 对象后返回 `baselineValidated=true`，再用检查点保存的原生字符身份投影云端单独文本变化。旧服务没有该核验回执时，Desk 拒绝开启回写。恢复后的 Office 保存必须生成不同于旧指针的新检查点，否则释放会话并继续 paused。

| 情况 | 处理 |
| --- | --- |
| 文件摘要未变，原生内容未变，映射有效 | 校验模型对象，恢复关联 |
| 文件摘要未变，云端发生已支持变化 | 由原生恢复产生的变化经过验证映射回写 Word，再保存与推进检查点 |
| 本地文件摘要变化，当前已支持对象与共同快照一致 | 允许原生恢复，不因 DOCX 重新打包误判；恢复保存后重新记录真实文件摘要 |
| 当前 Word 文字、段落顺序／身份、类型或已支持样式与共同快照不同 | 暂停并保留双方，不自动覆盖或合并本地分叉 |
| 检查点／原生缓存缺失或映射不能重建 | 暂停，提示关联状态需核对；可以打开云文档或建立显式新副本 |
| 原生缓存存在未确认操作 | 走原生恢复与未知结果核对，不能直接沿用文件摘要当成功 |
| 无编辑权限、账号不符、schema 不支持 | 暂停／拒绝，禁止缓存回放到其他租户 |

重新定位只接受相同源账号、租户、本地工作区和共同检查点 SHA-256 的唯一暂停候选，并要求用户确认旧／新路径；重名、pageId、路径相似度、同摘要多候选或已变化文件均不触发迁移。确认后仍执行完整恢复握手。首版没有“自动合并分叉”和“用本地覆盖云端”按钮；用户后续选择导入新页面属于新文件接入，不改原页面。对象核验只覆盖已支持的基础 Word 桥，不声明完整 DOCX 版式比较或任意外部修改合并能力；不支持的对象和失效映射继续拒绝。

## 4. 验收

扩充 W-08／W-14：正常关闭重开、云端单独变化、本地独立变化、两端均变化、原生缓存丢失、仅有状态向量、映射检查点过期、保存后关联文件写入失败、checkpoint 资源未写完时退出，以及账号／schema 切换。证明相同文件内容不被重复插入、旧模型不覆盖远端、分叉无静默丢失。未证明“云端单独变化后可安全重建映射并回写”，W-14 不能标记通过。

2026-11-10 本机 macOS ARM64 开发版验证：同路径 DOCX 与旧共同保存的字节摘要不同、14 个基础段落仍一致时，真实 Office 重开完成原生核验，关联恢复为 active，Office 保存后生成新的共同检查点，真实磁盘 SHA-256 与新检查点一致。原生 Yjs 回归覆盖云端单独插入后的投影，以及本地同长度文字替换、加粗／斜体、段落身份／类型／数量变化和映射损坏的拒绝。该结果不替代完整 Word 对象、结构并发或跨平台矩阵验收。
