# Design

## Context

本变更是日历路线图的远期阶段，依赖 `add-cloud-calendar-core`、`add-calendar-work-planning` 和 `add-team-calendar-collaboration` 已实施并稳定。它复用前三阶段提供的云端权威日历、事件版本与幂等、重复日程、提醒、团队授权、参与人和隐私安全忙闲契约，但不反向改变这些核心模型。参见 `proposal.md` 和四个 capability specs。

四个子域的故障边界不同：视频会议调用外部生命周期 API；资源预订要求本地强事务排他；公开预约暴露匿名入口；外部日历互操作是长时间运行的双系统一致性问题。它们可以关联同一日程，但不能因此共享一个状态机、连接器接口或发布命运。

供应商选择尚未作出，也没有任何会议或外部日历连接器被本设计声明为现已可用。每个候选连接器在实施前都必须完成 capability、OAuth、quota、数据处理和故障语义评审，评审产物决定该连接器能否进入只读、受控写回或会议生命周期实现。

## Goals / Non-Goals

**Goals:**

- 以四个清晰解耦的 bounded context 实现会议关联、资源预订、公开预约和外部日历互操作。
- 让每个子能力在前三阶段依赖满足后由独立 feature flag、迁移、权限和发布门禁交付。
- 对本地排他状态使用强事务，对外部副作用使用持久化工作流、幂等、补偿和对账。
- 保持核心日程模型供应商无关，并明确每份数据和每个字段的权威来源。
- 为公开入口、OAuth、webhook、配额、隐私、删除传播和运维恢复建立可审计边界。

**Non-Goals:**

- 不选择、承诺或预装具体视频会议或外部日历供应商。
- 不建立覆盖四个子域的统一 `Integration`、统一状态机或最低公分母连接器接口。
- 不将第三方系统提升为 JuggleWork 核心日历的隐式多主权威。
- 不在数据库事务中等待外部 API，也不承诺跨系统原子提交。
- 不绕过前三阶段的日历、参与人、忙闲、重复、提醒和授权服务重建平行实现。

## Decisions

### 1. 四个独立 bounded context 和发布单元

服务端划分 `Conferencing`、`ResourceBooking`、`AppointmentScheduling` 和 `ExternalCalendarInterop` 四个领域边界。每个边界拥有自己的表、Repository、授权服务、状态机、后台 worker、API 和指标；Desktop 也按相同边界提供设置、状态与恢复入口。它们仅通过稳定的 calendar/event/member 引用及显式领域命令或事件协作。

共享层只提供通用机制：租户身份、加密凭据引用、幂等命令、outbox/inbox、租约、退避、审计信封和脱敏遥测。共享机制不包含“创建会议或同步事件”之类的业务语义，也不规定四个子域必须采用相同状态。

选择该方案是因为四个子域的一致性、权限和外部能力差异大。备选的统一 Calendar Integration 聚合会把资源事务、匿名预约和游标同步压入同一抽象，形成耦合状态机和全局发布风险，因此拒绝。完全不共享基础机制则会复制凭据保护、重试和审计，并产生不一致的安全实现，也不采用。

### 2. 依赖门禁与独立 feature flag

四个子能力分别设置服务端读写 flag、worker flag 和 Desktop 展示 flag，并允许按 deployment、organization、member 或连接器逐步灰度。每个 flag 的启用条件包含：前三阶段所需契约版本可用、该子域迁移完成、权限和恢复路径验证通过、观测告警就绪。外部连接子能力还要求具体连接器评审通过。

flag 默认关闭。关闭某一子能力不会破坏核心日程读写，也不会关闭其他三个子能力；关闭 worker 时仍可读取状态但不接受会产生无人处理工作的新命令。跨子域增强采用显式可选编排，例如预约可选请求会议或资源，但基础预约成功标准不假定这些增强必然启用。

备选方案是单一生态总开关，实施更简单但无法独立灰度或隔离故障，与交付要求冲突，因此拒绝。

### 3. 日程保持核心，扩展关系由各子域拥有

核心 `CalendarEvent` 不增加供应商字段、资源占用列、公开 token 或外部同步游标。各子域使用稳定 JuggleWork event ID 建立关系：会议关联由 Conferencing 拥有，资源预订由 ResourceBooking 拥有，预约记录由 AppointmentScheduling 拥有，来源映射由 ExternalCalendarInterop 拥有。

核心日程可保存或读取经权限过滤的通用投影引用，例如“存在会议”“已预订资源”“来源为外部”，但投影不是子域的写入权威。日程删除或取消通过 outbox 领域事件通知订阅子域，各子域幂等处理并记录自己的最终状态。

备选方案是把所有扩展字段直接加入日程表。它会扩大核心模型、引入供应商耦合并使独立关闭和删除恢复困难，因此拒绝。

### 4. 本地事务与外部副作用采用不同一致性策略

资源预订是 JuggleWork 内部排他状态，必须在单个数据库事务内完成授权、策略、重叠检查、版本检查和占用提交。实现选择与生产数据库能力匹配的排他范围锁、序列化锁或等价约束，并通过并发集成测试证明重叠有效预订至多一个成功。多资源的原子预订在同一事务内排序获取锁，避免死锁并保证全有或全无。

会议、外部同步和跨子域预约增强涉及远程系统，采用本地事务写入业务状态与 outbox，再由 worker 执行外部调用。每次调用有稳定 operation/delivery ID、尝试记录、未知结果解析、有限重试和终态分类。补偿不是数据库回滚：例如日程已取消而会议取消失败时，日程保持取消，会议进入待补偿或人工处理。

备选方案是在日程事务内同步调用供应商，会造成长事务且无法解决响应丢失后的未知结果；使用分布式事务也不被多数外部 API 支持，因此拒绝。

### 5. 视频会议使用能力描述和窄连接器端口

Conferencing 定义本子域专用的能力描述，例如是否支持创建、更新哪些字段、取消、幂等键、按外部 ID 查询和 webhook。连接器只实现会议生命周期端口，不与日历同步连接器共享一个通用接口。会议关联保存 provider-neutral 状态、受保护的外部引用、连接信息投影、最后确认版本和操作状态；供应商原始响应仅在必要范围内加密保存并受保留期约束。

创建流程先提交待创建关联和 outbox，再调用连接器；成功后确认关联，未知结果先查询解析，确认孤立后才补偿取消。更新和取消同样以显式能力为门禁。周期性对账检测外部漂移，不静默改写核心日程字段。

备选方案是把专有 payload 放入 `CalendarEvent` 或强迫所有连接器支持完整 CRUD，前者污染核心模型，后者会把缺失能力伪装成成功，因此拒绝。

### 6. 资源目录与占用模型分离

ResourceBooking 将资源元数据/策略与时间占用分开。目录包含组织归属、时区、容量、设施、发现权限、开放时间和停用状态；预订包含资源、日程、时间范围、状态、版本和幂等身份。可用性查询读取策略与已提交占用，但其结果只是提示，提交事务必须重新验证。

停用资源阻止新预订，不级联删除已有预订。改期在同一事务内验证新时段后替换旧占用，冲突时保留原占用。无日程详情权限的调用者只得到忙闲块和策略级不可用原因。

备选方案是仅依赖查询后写入的乐观检查。两个并发请求可同时通过查询并造成双订，因此拒绝。

### 7. 公开预约以预约聚合为权威，不直接开放日历 API

AppointmentScheduling 拥有预约类型、公开 slug、规则版本、访客字段定义、预约、用途受限访问能力和滥用计数。公开可用性服务读取授权后的忙闲投影、资源可用性和已有预约，只返回可预约瞬时集合；公开端点不能查询底层日程详情。

所有规则以 IANA 时区保存，输出时段同时包含 UTC 瞬时和显示时区。前后缓冲参与冲突计算。提交时建立短期、防重复的服务端占位并在权威事务中重新验证，随后创建预约与主办日程；可选会议和资源作为显式后续编排，失败按类型补偿和展示，不留下被确认但没有主办日程的预约。

取消/改期链接使用高熵、散列存储、用途受限且可轮换的 capability token。公开端点采用分层限流、请求约束、可配置挑战和一致的不可用响应。邀请人字段按预约类型白名单收集，内容不进入日志或指标。

备选方案是让公开页面直接调用成员日历 free/busy 和 CRUD API。这会扩大匿名授权面、暴露内部标识并使隐私与限流难以隔离，因此拒绝。

### 8. 外部日历以映射、来源权威和同步账本驱动

ExternalCalendarInterop 拥有连接、日历映射、对象映射、同步游标、同步批次、墓碑、冲突和 outbound delivery。每个映射明确 `read-only` 或经评审的 `controlled-write-back`，并保存启用时的能力快照。对象映射记录外部稳定 ID、JuggleWork event ID、外部版本、JuggleWork 版本和最后同步基线。

初始导入按时间/分页边界分批执行，以映射和外部对象 ID 唯一约束去重。增量页与其对象变更在本地幂等提交后才推进游标。webhook 只触发拉取，不直接作为变更内容的权威；验证、去重后唤醒同步。周期性补偿扫描覆盖 webhook 丢失、乱序及不支持 webhook 的连接器。游标失效启动有界重建并显式标记陈旧状态。

字段与生命周期权威按映射定义。只读映射拒绝本地写回；受控写回只开放评审确认的对象、字段和操作。双方从同一基线后修改同一字段时创建冲突，保留双方版本；不采用静默 last-write-wins。永久错误、授权失效和配额延迟进入不同状态，避免无限重试。

备选方案是以 webhook payload 直接更新、将本地和外部都视为无条件多主或只维护时间戳。它们分别无法覆盖丢事件、无法确定权威和无法可靠检测冲突，因此拒绝。

### 9. 断连与删除是显式状态转换

外部连接区分主动暂停、OAuth 失效和用户断连。断连先禁止新 worker 租约和写回，再撤销可撤销授权、删除本地凭据材料、停用 webhook，并让用户选择保留来源标记副本或删除导入副本。断连不自动把副本转换为无来源的原生日程。

同步删除使用墓碑记录映射、来源版本、方向和处理结果，以阻止增量重放、初始扫描或双向回环重新创建对象。外部权威删除可墓碑化导入对象；受控写回的本地删除先提交意图和本地墓碑，再投递外部删除。永久失败成为显式冲突，不谎报远端已删除。

会议和预约也保留必要的取消墓碑及 operation ID，直到重放和补偿窗口结束。保留期限到期后按隐私政策清除敏感 payload，但保留非敏感去重证据所需的最小摘要。

备选方案是在断连时立即硬删所有映射和账本，会失去恢复、审计及防重依据，因此拒绝。

### 10. 凭据、权限和数据最小化集中治理

OAuth token 和 webhook secret 使用现有服务端凭据边界加密保存，业务表仅存 credential reference。每个连接器请求最小 scope，scope 扩大必须重新评审和显式授权。token、加入秘密、公开 capability、访客字段及外部原始 payload 不进入普通日志、错误信息或分析事件。

服务端在每次查询和变更时执行组织、成员、日历、事件及子域权限；Desktop 隐藏按钮不构成授权。webhook 在解析业务 payload 前完成签名、时效、连接范围和重放验证。公开预约响应统一模糊内部不可用原因，防止日历和预约枚举。

备选方案是让 Desktop 持有第三方长期凭据或只在连接时检查权限。它们分别扩大终端泄露面和无法处理撤权，因此拒绝。

### 11. 子域级观测、审计和运维恢复

所有异步工作使用结构化关联键：organization、subdomain、mapping/association/booking ID、operation/delivery ID 和不含内容的错误分类。指标至少覆盖队列积压、延迟、重试、未知结果、永久失败、补偿、游标陈旧、webhook 验证失败、配额退避、资源冲突、公开限流和授权拒绝。

审计记录谁在何时启用连接器、改变映射/权威、管理资源、发布预约类型及发起高影响生命周期操作。运维入口按子域提供暂停、重试、重新同步、对账和查看脱敏诊断，不能使用一个“全部重试”动作跨域重放。

告警和 SLO 也按子域与连接器模式拆分，避免一个供应商故障将本地资源预订标记为不可用。分析事件只记录能力和结果类别，不记录日程内容、访客答案、token 或会议秘密。

备选方案是仅依赖通用 HTTP 错误率，无法观察积压、陈旧和部分成功，因此拒绝。

## Risks / Trade-offs

- [四个边界增加表、worker 和管理入口数量] → 使用共享的安全基础机制和一致运维信封，但保持业务状态机独立；按子域分批交付。
- [跨子域编排产生部分成功] → 核心业务先提交，外部增强使用持久化工作流、明确状态、幂等补偿和人工恢复；不承诺虚假的跨系统原子性。
- [数据库对时间范围排他的支持因方言而异] → 实施前验证生产数据库能力，选定可证明串行化的锁或约束方案，并以真实并发集成测试作为发布门禁。
- [供应商能力和配额变化] → 能力快照版本化，连接器评审包含配额容量模型；能力降级时自动关闭不再安全的写操作而非模拟成功。
- [同步游标或 webhook 丢失导致数据陈旧] → 游标提交后移、补偿扫描、陈旧水位指标和有界全量对账共同覆盖。
- [双向写回导致冲突和删除回环] → 默认只读，写回逐连接器启用；保存同步基线、冲突记录和墓碑，禁止静默 last-write-wins。
- [公开预约被枚举或滥用] → 最小响应、分层限流、挑战、用途受限 token、内容脱敏和异常告警；容量测试通过前不开放。
- [外部或访客数据扩大隐私范围] → 最小 scope、字段白名单、加密凭据、保留期和删除流程；上线前执行独立安全与隐私评审。
- [feature flag 组合增加测试矩阵] → 定义各子域关闭、单独开启和受支持组合的契约测试；跨域增强不成为基础能力的隐式前提。
- [前三阶段接口尚未稳定] → 本阶段 flag 保持关闭；实施开始前冻结所需 event、free/busy、权限、重复和同步契约版本。

## Migration Plan

1. 确认前三阶段已完成发布门禁，冻结本阶段依赖的日历、事件、参与人、忙闲、重复和授权契约；未满足时不启用任何本阶段 flag。
2. 为四个 bounded context 分别增加向后兼容表、索引、权限和关闭状态的 API/worker 骨架；不修改核心日程的供应商字段。
3. 建立共享的凭据引用、outbox/inbox、幂等投递、审计和脱敏观测机制，并通过安全测试。
4. 分别实施和验证本地资源事务、公开预约安全边界、会议补偿工作流和外部同步账本；各子域可按风险与产品优先级独立推进。
5. 在实现任何具体连接器前完成其 capability/OAuth/quota/data-handling review，记录能力矩阵和上线模式；评审不通过则保持不可配置。
6. 先以内部组织或测试连接器验证只读/无外部副作用路径，再按子域开启 worker、服务端写入和 Desktop UI 灰度。
7. 外部日历先启用已评审连接器的只读模式；受控写回在冲突、断连和删除传播演练通过后单独灰度。
8. 每次扩大灰度前验证队列水位、配额、补偿、隐私、限流、并发冲突和恢复演练，并保存不含敏感内容的发布证据。
9. 回滚单个子域时先关闭新写入和公开入口，再停止或排空对应 worker；保留表、墓碑、游标和待补偿记录。恢复后从持久化状态继续，不执行破坏性降级。
