# Design

## Context

本变更建立在 `add-cloud-calendar-core` 与 `add-calendar-work-planning` 已实施且通过模型、权限、同步、重复实例、提醒和 Agent 操作验证的前提上；未满足该前置门槛时不得启用本变更。前两阶段提供云端权威 Calendar/CalendarEvent、稳定 ID、版本和幂等写入、增量游标、按租户隔离的 Desktop 缓存、重复系列与实例例外，以及不依赖页面挂载的 Agent 能力。本设计只说明团队协作如何扩展这些契约，动机见 `proposal.md`，可观察行为见三个 capability specs。

本变更跨 `jugglework-server` 和 `jugglework-desktop`，扩大了对象级和字段级授权边界。最危险的失败模式不是显式拒绝，而是旧缓存、批量查询、通知预览、搜索索引、冲突响应或 Agent 上下文在降权后继续携带详情。因此权限必须由服务端在每个读取和写入入口统一裁决，客户端只消费已经裁剪的投影，不能承担安全过滤职责。

本阶段只有组织内部身份。目标成员必须由服务端从当前组织目录解析为有效成员，不接受自由文本邮箱或外部身份。会议服务、会议室、预约和外部日历同步留给后续 `add-calendar-meeting-ecosystem`，不得为它们预埋可绕过当前组织边界的半成品入口。

## Goals / Non-Goals

**Goals:**
- 在现有个人日历模型上增加组织团队日历及 `free-busy`、`viewer`、`editor`、`manager` 的单调权限层级，并使所有入口默认拒绝。
- 把 CalendarMembership 与 EventAttendee 建模为独立聚合，在不隐式互相转换的前提下支持邀请、响应、更新、取消及重复实例范围。
- 以服务端字段投影保证忙闲查询最多泄露时间区间，同时支持冲突提示和共同可用时间建议。
- 使授权、参与和可用性变更通过版本化增量事件在多端收敛，尤其保证撤权、降级和组织成员失效会清除客户端敏感缓存。
- 让 Desktop、后台同步和 Agent 使用相同的服务端身份、授权、版本、幂等和审计契约。
- 通过 feature flag、shadow 观测和分批组织灰度降低权限模型和高并发协作上线风险。

**Non-Goals:**
- 外部联系人、跨组织邀请或任意邮箱参与人。
- 视频会议创建或供应商连接、会议室及其他资源预订。
- 公开预约页面、预约类型、外部日历导入/写回或供应商同步。
- `this-and-following` 重复范围和任意复杂 RRULE 编辑；只复用前一阶段支持的单实例与整个系列。
- 离线写入、客户端权威冲突解决，或在无法重新鉴权时继续展示协作缓存。
- 用日历成员批量自动生成参与人，或用参与人身份自动授予日历发现、搜索和范围读取权限。

## Decisions

### 1. 前两阶段是硬启用依赖，而不是运行时兼容分支

实现与灰度门槛要求 `add-cloud-calendar-core` 和 `add-calendar-work-planning` 的数据库迁移、增量同步、重复实例和 Agent 授权均已稳定。协作 schema 可以在 flag 关闭时提前部署，但 API、Desktop 入口和 Agent affordance 只有在依赖能力版本满足且组织 flag 开启时才可见。

不为缺少前置能力的部署维护降级实现。例如，没有实例例外模型时不允许退化成“修改整系列”，没有权限游标时不允许仅依赖缓存 TTL 撤权。替代方案是各子能力自行探测并部分启用；拒绝该方案，因为会产生无法解释的跨部署语义和安全缺口。

### 2. CalendarMembership 与 EventAttendee 是两个独立聚合

`calendar_memberships` 表达成员对日历容器的访问，唯一键为 `(calendar_id, organization_member_id)`，包含角色、授权版本、授予/撤销信息和生命周期状态。日历创建者产生初始 `manager`，最后一个有效 manager 受数据库事务内保护。

`event_attendees` 表达成员对某个事件系列或实例的参与关系，唯一键按作用范围分别约束系列记录或实例覆盖，包含邀请版本、响应状态、响应版本、邀请/取消状态及组织成员引用。系列默认参与关系与单实例覆盖沿用重复模型的“系列 + 例外”合并规则，不复制未来每个实例。

两者只共享不可变组织成员 ID，不以成员表外键联动创建或删除。撤销 CalendarMembership 不删除 EventAttendee；组织成员失效则同时使两种能力在授权层失效。替代方案是参与人作为日历成员的附属角色；拒绝该方案，因为受邀者的最小邀请访问和整个日历的范围访问具有不同生命周期，合并会造成权限升级与撤权歧义。

### 3. 统一授权器返回能力集合和字段投影

服务端提供一个日历领域授权器，以 deployment、organization、actor member、目标 calendar/event、CalendarMembership、EventAttendee 和当前组织成员有效性为输入，返回明确能力集合，例如 `read_free_busy`、`read_details`、`write_events`、`manage_calendar`、`respond_self`，以及允许字段投影。角色层级只用于计算能力，业务 handler 不直接比较角色字符串。

所有 REST/内部工具入口、搜索、批量查询、增量同步、通知渲染和 Agent affordance 调用同一授权器。Repository 返回领域对象给服务层后，服务层在序列化、写通知 outbox 或写同步日志之前应用投影；客户端不会收到“完整对象 + 请自行隐藏”的响应。权限不足与对象不存在使用统一的非枚举结果，授权失败优先于版本冲突，避免泄露当前版本。

`free-busy` 投影只输出归一化半开区间和非稳定忙碌状态，不输出事件、日历或参与人可关联标识。相邻和重叠区间在授权边界内合并。拥有详情权限的调用方使用 free-busy 端点时仍得到同一最小投影，防止调用入口决定隐私语义。

替代方案是让每个 API 和 Desktop 组件分别维护字段列表；拒绝该方案，因为遗漏一个搜索、通知或 Agent 路径就会泄露字段，而且角色扩展时无法证明一致性。

### 4. 组织成员有效性是每次授权的前置条件

授予 CalendarMembership 或 EventAttendee 前必须以当前组织目录确认目标是有效成员。读取、写入、响应、通知投递和同步时再次检查 actor 与目标成员状态。成员停用或移出组织会生成 organization-member-invalidated 领域事件，由日历服务将其解释为所有相关 CalendarMembership 和 EventAttendee 的失效，不物理删除审计记录。

重新加入组织会获得新的有效性周期；历史授权和邀请不自动恢复，必须显式重新授予或邀请。替代方案是仅在创建关系时校验成员，随后依赖目录异步清理；拒绝该方案，因为事件积压期间会形成真实越权窗口。

### 5. 授权事件是撤权和多端缓存失效的主通道

每次成员授予、角色变化、撤权或组织成员失效都在同一数据库事务中增加单调的 `authorization_version`，并写入 transactional outbox。事件至少包含 organization、calendar、subject member、旧/新角色或失效原因、权限版本和时间，不含日程字段。

增量同步把权限事件置于内容事件之前处理。客户端收到撤权后删除日历详情、事件实体、范围结果、搜索索引、通知预览、忙闲和共同可用候选；降级后按新投影裁剪或重新拉取。服务端同步接口对旧游标重新鉴权，并可返回 `authorization_reset_required`，所以漏掉实时推送的离线设备仍会在恢复同步时清除数据。

Desktop 缓存键扩展为 deployment + organization + actor member + calendar/subject + authorization version + query scope。应用启动、账户/组织切换、离线恢复和旧详情路由打开时先做轻量授权刷新；无法验证时不渲染敏感缓存。实时事件只用于降低延迟，不是正确性的唯一来源。

替代方案是短 TTL 后自然过期；拒绝该方案，因为 TTL 窗口内仍可查询或离线展示已撤销详情，也不能清理全文搜索等派生数据。

### 6. 邀请和通知使用版本化状态机与 transactional outbox

参与人状态机区分邀请生命周期 (`active`, `cancelled`, `invalid-member`) 与响应 (`needs-action`, `accepted`, `declined`, `tentative`)。每次参与人集合、邀请版本或响应变化都使用目标版本和幂等键写入；同一基础版本的并发写入只允许一个成功。

新增邀请、实质更新、参与人移除、日程取消和响应变化在领域事务内写 notification outbox，事务外异步投递。逻辑通知以事件/实例、参与人、通知类型和邀请版本去重。失败投递可重试，不回滚领域状态。投递和打开通知时重新鉴权并按当前能力渲染；若已撤权、降级或成员失效，则取消投递或使用不含详情的最小提示。

时间、时区或重复范围变化会提升 invitation version 并设置 `reconfirmation_required`，保留旧响应作为审计而不把它当作新安排确认。标题等非排期实质变化保留当前响应。哪些字段触发重新确认使用服务端固定分类，不由客户端决定。

替代方案是写入后由 handler 直接发送通知；拒绝该方案，因为事务成功但发送失败会丢通知，重试写入又会重复投递，并且难以在投递前重新鉴权。

### 7. 重复参与关系采用系列默认值加实例覆盖

参与人变更和响应 API 强制携带 `scope: this-instance | entire-series`。系列记录定义默认参与人和默认响应语义，实例覆盖只保存与系列不同的添加、移除、响应、更新或取消状态。查询具体实例时先展开系列，再按实例例外合并。

系列更新只影响匹配系列默认关系的实例，不覆盖显式实例例外。系列取消对未来活动实例产生取消效果，单实例取消只写实例例外。通知根据合并后的实际影响计算，不按潜在实例盲目广播。`this-and-following` 在 API 类型和校验层明确拒绝，而不是近似为整个系列。

替代方案是为每个未来实例物化参与人；拒绝该方案，因为无限重复、规则变化和并发例外会造成大量更新、重复通知和难以证明的收敛问题。

### 8. 忙闲计算在服务端以最小投影执行

availability 服务接收组织内主体、有限时间范围、IANA 时区、时长、工作时段和粒度。它先逐主体授权，再从当前有效实例与参与状态生成忙碌区间；取消、已拒绝和失效参与关系不占用，`accepted`、`needs-action` 与 `tentative` 的占用语义由组织级固定策略解析并在所有入口复用。

服务内部可以读取必要事件数据，但对外只返回合并区间、未知状态或候选时间。共同可用时间通过授权后的区间补集求交，应用工作时段和时长后，以“最早开始、最少跨时区非工作时间、稳定主体顺序”的确定性规则排序。任何主体无权或状态未知时，不将缺失数据视为空闲。

冲突预览返回主体与重叠区间，不返回造成冲突的事件。预览响应带 `availability_token`，包含参与主体、权限版本、事件/响应水位和请求约束的签名摘要。最终创建或改期仍在事务边界前重新授权和重新计算；token 只用于发现陈旧预览，不是锁，也不保证时段预留。

替代方案是将各成员事件详情下载到 Desktop 再计算；拒绝该方案，因为会向不需要详情的客户端泄露数据，并使 Agent 与 Desktop 难以维持同一隐私边界。

### 9. 多成员并发使用乐观版本、幂等键和最终写入重检

沿用核心日历的 event version 和 idempotency contract，并为 membership、attendee response 与 invitation version 增加各自版本。管理操作在事务内锁定日历成员集合的必要行并验证至少保留一个 manager；响应操作只竞争该参与人的当前版本，避免无关参与人互相阻塞。

多个 manager 并发改同一授权、多个设备并发响应、更新与取消并发时，数据库条件写入决定唯一获胜者，失败者收到不含无权字段的冲突。取消是终止态，不能被旧响应重新激活。共同可用建议不是预订锁；最终写入重新计算冲突，必要时要求再次确认。

服务事件具有组织范围顺序号和实体版本。客户端可以重复或乱序接收，但只能应用更高版本；权限撤销的效果优先于内容更新。替代方案是全组织悲观锁；拒绝该方案，因为会不必要地串行化无关日历和成员，同时仍不能跨用户思考时间持锁。

### 10. Desktop 与 Agent 共享 API，但保留不同交互确认

Desktop 团队设置、成员角色、参与人响应和排期 UI 只调用服务端领域 API，并根据返回能力启用界面；禁用控件不是授权边界。Agent 的查询和写入 affordance 调用完全相同的 API，actor 来自当前认证组织成员，不接受模型传入 actor 或角色。

Agent 输出只包含服务端投影。参与人批量变化、取消、整个系列变化以及忽略冲突继续写入属于高影响操作，必须先生成服务端预览，显示目标成员、实例范围、通知影响和隐私安全冲突，再由用户确认；执行时重新鉴权和重检版本。权限在预览与执行间变化时拒绝操作。

替代方案是为 Agent 提供更宽的内部接口以提升自然语言能力；拒绝该方案，因为工具授权或工作区权限不能替代组织和日历权限，且更宽接口会破坏 Desktop/Agent 一致性要求。

### 11. 安全与隐私采用矩阵测试和负向契约测试

测试建立 actor × 组织成员状态 × 日历角色 × 参与人状态 × 入口矩阵，覆盖直接 ID、列表、范围、搜索、批量、同步、通知、Desktop 和 Agent。每个允许场景断言字段白名单，每个拒绝场景断言状态、响应体、计数、排序占位和日志均不泄露对象存在性或敏感字段。

专门的撤权测试在查询、通知排队、增量同步、离线缓存和 Agent 确认之间插入降级/撤权；验证详情不能从旧游标、旧 token、旧通知或本地索引恢复。忙闲测试验证区间合并、防窄窗口重建的限流、无稳定事件 ID，以及无权主体不会被解释为空闲。组织隔离测试使用相同 UUID 形状和已知 ID 探测跨租户访问。

所有服务日志、指标和 tracing 使用成员/日历的受控标识与结果码，不记录标题、描述、参与人完整列表或忙闲区间集合。安全测试进入灰度前阻断门槛，而不是上线后的补充项。

### 12. 按 schema、shadow、内部组织、分批组织四阶段灰度

部署使用独立 feature flags：服务端读写总开关、Desktop 导航/管理 UI、Agent affordance、availability 建议。阶段如下：

1. 在功能关闭时部署向前兼容 schema、索引和 outbox consumer，验证迁移及回滚兼容。
2. 开启 shadow 授权与 availability 计算，只记录现有 owner 访问与新授权器是否一致、查询成本和区间统计；shadow 日志不得持久化敏感字段，且不向用户返回协作结果。
3. 对内部测试组织启用团队共享和参与人，再单独启用 availability；执行双设备、三成员角色矩阵、撤权和并发验收。
4. 按组织百分比分批扩大 Desktop，稳定后才暴露 Agent affordance；监控拒绝率、授权重置、通知重试、缓存清除确认、冲突率和查询延迟。

flags 只控制能力是否可用，不绕过授权。灰度关闭时拒绝新的协作写入，保留已有数据和审计；读取根据回滚阶段选择安全只读或完全关闭，绝不回退成 owner 以外的未过滤读取。

## Risks / Trade-offs

- **[Risk] 字段投影遗漏搜索、通知、日志或 Agent 某一路径导致隐私泄露** → 统一授权器和投影 DTO；禁止领域对象直接序列化；字段白名单、快照和负向契约测试覆盖全部入口。
- **[Risk] 撤权实时事件丢失使离线或休眠设备保留详情** → 服务端每次查询重新鉴权，增量同步支持 authorization reset，应用恢复前验证权限，本地按权限版本清除实体和派生缓存。
- **[Risk] 仅有忙闲权限仍可能通过高频窄窗口推断日程结构** → 合并相邻区间、限制最小粒度/范围/频率和批量主体数，无稳定事件标识，并对枚举式请求审计与限流。
- **[Risk] 成员与参与人分离增加理解和查询复杂度** → 在领域类型、API 和 UI 中使用不同名称与入口；只共享组织成员引用；用明确能力解释成员可见性和邀请可见性。
- **[Risk] 系列默认与实例覆盖在并发更新时产生通知重复或遗漏** → 基于邀请版本计算合并后的实际影响，以实例/系列 + 参与人 + 通知类型 + 版本作为 outbox 去重键，并加入系列/实例竞态测试。
- **[Risk] 共同可用时间在计算后立即陈旧** → 候选明确是建议而非预订，返回 availability token，最终写入重新计算并展示新冲突。
- **[Risk] 多成员批量查询和候选计算造成数据库压力** → 限制时间范围及主体数，按授权后的时间桶缓存，针对实例范围和参与关系建立索引，灰度监控 p95/p99 与查询放大。
- **[Risk] 组织成员失效事件延迟** → 每次授权直接检查当前成员有效性，目录事件只负责主动失效和缓存清理，不作为拒绝访问的唯一依据。
- **[Risk] 通知在权限变化后泄露旧标题或参与人** → outbox 保存引用和通知类型而非预渲染正文，投递/打开时重新鉴权并渲染；无法授权则降级或取消。
- **[Risk] feature flag 回滚留下客户端无法理解的数据** → schema 和客户端读取保持向前兼容；关闭写入口前先停 Agent 与 Desktop 入口；不删除协作数据；重新开启后从服务端版本恢复。

## Migration Plan

1. 验证两个前置 change 的实施版本、重复/同步/权限安全测试和生产观测满足门槛；未满足则停止本变更部署。
2. 在 flags 关闭时部署 CalendarMembership、EventAttendee、响应/通知 outbox、权限版本与审计 schema；执行迁移回滚演练和索引负载测试。
3. 部署统一授权器、投影、权限事件 consumer 和新 API，但保持组织默认关闭；运行 owner 访问 shadow 对比与全量安全测试。
4. 发布能够理解权限 reset、角色投影和邀请状态的 Desktop 版本；旧客户端看到协作日历时必须安全隐藏或要求升级，不能按个人日历完整缓存。
5. 对内部组织启用共享与参与，完成至少三名成员、两个设备、四角色、组织成员失效、重复实例和并发验收。
6. 单独启用 availability 与冲突提示，验证区间披露、限流、性能和 stale-token 重检后再逐组织扩大。
7. Desktop 稳定后启用 Agent affordance，对比相同 actor 在 Desktop 与 Agent 的允许/拒绝及字段投影结果。

回滚优先关闭 Agent、availability、Desktop 入口和新写 API，停止产生新协作变更；保留 schema、成员/参与人数据、outbox 和审计以便恢复。若授权或字段投影存在泄露风险，立即关闭所有协作读取并向已启用客户端发布 organization-level authorization reset，清理本地协作缓存。仅在确认数据不再需要且经过独立迁移后才删除 schema，本次灰度回滚不做破坏性降级。
