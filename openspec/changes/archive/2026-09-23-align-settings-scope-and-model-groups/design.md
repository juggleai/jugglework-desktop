## Context

设置页有「工作区」「全局」「云端」三个分组，分组本身没有约束力：它只决定侧栏位置和工作区切换器是否出现，具体作用域由各视图自己选择的存储决定。两者一旦不一致，用户就会得到错误的心智模型。

模型组页面同时承载两类来源完全不同的条目：用户在本机 OpenCode 配置里声明的本地模型组，和组织通过云端下发并导入的托管模型组。两者的生命周期、可操作范围都不同，混排在同一列表会让"能做什么"变得不可预测。

停用一个模型组不是删除配置，而是把它的 ID 写进 `disabled_providers`。这份列表存在多个来源：用户全局 `opencode.jsonc`、工作区项目配置、以及服务端按工作区维护的运行时层。运行时层的写接口是整表替换，因此"以什么为基准计算下一份列表"直接决定会不会波及其他条目。

## Goals / Non-Goals

**Goals:**

- 设置页分组与配置的实际作用域一致，工作区切换器只在按工作区生效的页面出现。
- 自动压缩上下文一次设置、在当前运行环境的所有工作区生效，默认开启。
- 模型组按来源分区，可操作范围与来源匹配。
- 停用与恢复只影响被操作的那一个模型组。

**Non-Goals:**

- 不改变通用页其余四个开关的存储位置，它们本来就是全局的。
- 不把自动压缩设置同步到云端账号或其他设备。
- 不改变组织托管模型组的下发、导入与凭据链路。
- 不引入模型组列表的手动排序能力。

## Decisions

**D1：分组按"配置写到哪里"划分，而不是按"在哪里被用到"。**
判据是同一账号下切换工作区后设置值是否变化。通用页四个本地存储开关加上全局化后的自动压缩都不随工作区变化，因此整页归入全局分组；扩展页的 MCP、技能、插件都按 workspaceId 读写，留在工作区分组。工作区切换器继续由 `getWorkspaceSettingsTabs()` 驱动，无需额外判定。

**D2：自动压缩写入全局 OpenCode 配置文件，并清理工作区运行时层同名键。**
沿用 `globalize-local-model-groups` 已确立的全局作用域边界（当前运行环境的 `OPENCODE_CONFIG_DIR`），复用 `readOpencodeConfigFile` / `writeOpencodeConfigFile` 的 `global` scope。
OpenCode 的配置合并中工作区级优先于全局级，因此工作区运行时层残留的 `compaction.auto` 会静默压过新的全局值。清理不是可选项：开关写入全局成功后必须清除当前工作区运行时层的 `compaction`，否则用户会看到开关状态与实际行为不符。
读取时 `compaction.auto` 未设置一律视为开启，保持与既有默认行为一致。

**D3：Server 用显式 `null` 表达"清除 compaction"。**
`PATCH /workspace/:id/config` 现在只在 `compaction` 是对象时合并，没有删除语义。约定 `compaction: null` 为清除，与 `provider` 字段已有的"显式 null 删除"约定一致，避免为一个键新增接口。

**D4：模型组按来源分区，可操作范围由来源决定。**
本地模型组保留查看详情、断开、重新连接、彻底删除。组织托管模型组只读：它由组织统一下发，用户端的"断开"既不影响组织侧配置，又会造成本地与组织状态不一致，因此移除该入口并标注由组织管理。分区标题使组织托管条目的只读性无需逐条解释。

**D5：停用列表以工作区运行时层为写入基准。**
既有实现从引擎的 `config.get()` 取 `disabled_providers`，那是合并后的有效配置，包含用户全局配置和项目配置声明的停用项。把它整体回写进按工作区整表替换的运行时层，等于把其他来源的停用项固化到这个工作区——用户之后从全局配置里移除该项也不再生效。改为先读运行时层当前列表，只对其做单项增删。

**D6：停用项标识统一按不区分大小写比较。**
列表渲染已按小写归一判断条目是否停用，而写入按精确字符串增删。大小写不一致时会出现"显示已断开但重新连接无变化"。以小写作为唯一比较口径，写入时保留首次记录的原始大小写。

**D7：忙碌状态按条目隔离。**
进行中的断开、重连、删除只禁用该条目自身的按钮。跨条目禁用会让用户以为一次点击影响了整张列表，且掩盖了条目位置变化。

**D8：列表排序键与连接状态无关。**
断开后条目会从引擎列表中消失、退回本地缓存渲染，缓存缺失时名称退化为 ID，按名称排序会导致位置跳动，用户在同一屏幕位置连续点击就会命中不同条目。排序改用 provider ID，与连接状态和缓存命中与否无关。

## Risks / Trade-offs

- 全局化后，一个工作区关闭自动压缩会影响所有工作区，这是目标行为；清理工作区遗留值意味着此前刻意为单个工作区设置过该开关的用户会回到全局值。影响面小于状态与行为不符的代价。
- 组织托管模型组失去用户侧断开入口后，只能由组织在云端取消发布。这是所有权的正确归位。
- 停用列表改以运行时层为基准后，用户在全局配置里手工写的停用项不再被复制进运行时层——这正是要修的行为，但依赖旧串扰效果的工作区在升级后会恢复成全局配置的真实状态。
- 排序改用 provider ID 后，列表不再按显示名的中文拼音顺序排列。稳定性优先于字母序。

## Migration Plan

1. 先发 Server 的 `compaction: null` 清除语义，旧客户端不受影响。
2. 客户端切换自动压缩读写链路；首次切换开关时顺带清理当前工作区运行时层遗留值，不做后台批量迁移。
3. 分组调整与模型组改动为纯前端渲染变更，无需数据迁移。
4. 停用列表基准切换后，既有工作区运行时层中被串扰写入的条目在用户下次断开或重连时自然收敛，不主动改写用户配置。
