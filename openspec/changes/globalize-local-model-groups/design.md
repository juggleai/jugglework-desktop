## Context

模型组认证信息与 provider 配置由不同链路维护：认证状态用于判断是否连接，OpenCode 配置保存模型、Base URL 等运行参数。旧实现把用户新增 provider 写进工作区配置，因此工作区切换和认证状态变化都会影响列表可见性。

## Goals / Non-Goals

**Goals:**

- 自定义模型组在同一运行环境内跨工作区可见和可用。
- 生产版与 dev 版保持配置隔离。
- 本地模型组具备稳定的详情、编辑、断开与重新连接体验。
- 兼容旧工作区级配置并在用户保存时自然迁移。

**Non-Goals:**

- 不把配置同步到其他设备或云端账号。
- 不合并生产版与 dev 版的配置目录。
- 不改变内置 provider 的认证协议和模型发现方式。

## Decisions

**D1：全局作用域以当前运行环境的 `OPENCODE_CONFIG_DIR` 为边界。**
App 和 Server 统一从该目录解析全局 OpenCode 配置；工作区配置不再作为新增自定义模型组的目标。这样同一运行环境内的所有工作区共享配置，同时生产版和 dev 版仍可通过不同目录隔离。

**D2：迁移采用保存时覆盖全局、再清理工作区旧副本。**
已有工作区级 provider 在用户编辑保存时写入全局配置；全局写入成功后才移除同 ID 的工作区配置，避免迁移中断造成数据丢失。删除时同时清理全局配置和可能遗留的工作区旧副本。

**D3：列表身份与连接状态分离。**
本地模型组是否存在由配置与本地缓存共同决定，连接状态只控制状态标签和可用操作，不再决定条目是否渲染。重新连接期间也保留原条目，成功后原地更新状态。

**D4：详情与编辑复用同一弹窗。**
点击本地模型组直接打开只读详情，用户可切换到编辑态。编辑态锁定 provider ID；API Key 未填写时沿用已保存凭据，避免查看后保存意外清空密钥。

## Risks / Trade-offs

- 同一运行环境内多个工作区会立即共享自定义模型组变更，这是目标行为；界面使用「本地」标签提示该配置来自本机。
- 旧工作区配置不会在后台批量迁移，只有保存或删除时收敛，降低静默修改用户配置的风险。
- 断开条目依赖已加载配置或当前会话缓存保留展示信息；连接成功后以运行时返回数据刷新。

## Migration Plan

1. App 与 Server 统一识别 `OPENCODE_CONFIG_DIR` 下的全局配置。
2. 新增和编辑自定义模型组只写全局配置。
3. 编辑旧工作区模型组时完成单条迁移；删除时清理两处可能存在的副本。
4. 回滚代码不会删除全局配置，用户仍可从 OpenCode 配置中恢复已有 provider。
