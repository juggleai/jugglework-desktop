  **Four more real bugs found only by doing this, none catchable by static review or the mocked-client unit tests:**
  1. `isHiddenConversationUpdate`'s `conversation.latestMessage` guard had the *same* sender-id-fallback bug as 4.2's message-handler fix, independently — `isAutomationEventPushMessage(latestMessage)` matches the visible notification too, so the conversation's own update was being silently dropped by `mergeConversations`, keeping the conversation out of the list entirely. Fixed by extracting a shared, directly-unit-testable predicate (`isHiddenAutomationConversationMessage`, `automation-event-message.ts`) that both the message handler and `mergeConversations` now call — the previous unit test for this only asserted source-text substrings, never called the real logic with a realistic message object (both `name` and `sender.id` set together, the exact shape a real message has); the new test does, and would have caught this.
  2. **The content-shape assumption copied from `parseAutomationReadinessUnblockedPayload` was wrong.** The vendor IM SDK parses `msg_content` (the server's marshaled JSON) and flattens its fields directly onto `message.content` — `message.content.automationId`, not `message.content.content` holding a JSON string to re-parse. This was never actually verified against a real message before (only against hand-constructed test fixtures that encoded an assumption, not an observed fact) for either message type. Fixed `parseAutomationTriggerNotificationPayload` to read fields directly off `content`. **`parseAutomationReadinessUnblockedPayload` (pre-existing, shipped, unrelated to this change) almost certainly has the identical bug** — same send path, same wrapping assumption — flagged to the user, not fixed here since it's a separate already-shipped feature outside this change's scope.
  3. `messagePreview` (`components.tsx`) has its own independent `message.name` dispatch table (unrelated to `MESSAGE_NAMES`/`SUPPORTED_MESSAGE_NAMES`), defaulting to "[暂不支持的消息]" for unregistered names — the conversation-list row preview showed that literal text for the new message type even after 5.1's fix made the message itself render correctly. Added a case reusing the bubble's own `bubbleCopy`/`resolveAutomationTriggerBubbleTemplate`, not a separate preview-text implementation.
  4. `conversationName` only resolves a display name from `conversationAlias`/`conversationTitle`/a contacts directory — `jw-automation-events` isn't a real contact, so it fell back to showing the raw sender id even though the nickname registration (2.1) had genuinely succeeded (`message.sender.name` was already the correct "自动化通知" on the real received message). Added a fallback to `conversation.latestMessage?.sender?.name`, ordered after the contacts-directory lookup so a real contact's real name still wins.
