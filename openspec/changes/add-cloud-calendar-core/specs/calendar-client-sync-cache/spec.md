# Spec Delta

## Purpose

定义 Desktop 日历客户端的增量刷新、范围缓存和离线边界，使跨设备数据以云端为准，同时防止不同 deployment、组织或成员之间发生数据泄漏。

## ADDED Requirements

### Requirement: 缓存按 deployment、organization 和 member 分区
客户端 MUST 使用 deployment、organizationId 和 memberId 的联合身份分区 Calendar、CalendarEvent、范围覆盖、变更游标和草稿，任何读取或写入不得跨分区复用数据。

#### Scenario: 同一成员位于不同组织
- **WHEN** 同一 memberId 在两个 organization 间切换
- **THEN** 客户端为每个 organization 使用不同缓存分区且不在新组织视图中显示旧组织数据

#### Scenario: 不同 deployment 使用相同身份标识
- **WHEN** 两个 deployment 中出现相同 organizationId 和 memberId
- **THEN** 客户端仍将其缓存、游标和草稿完全隔离

#### Scenario: 缓存键缺少租户维度
- **WHEN** 客户端无法确定完整 deployment、organizationId 或 memberId
- **THEN** 客户端不得读取或写入受保护日历缓存并不显示先前身份的数据

### Requirement: 身份切换先隔离后加载
客户端 SHALL 在 deployment、organization 或 member 身份变化时立即停止展示原分区数据，取消其进行中请求，并仅在新身份确认后读取新分区。

#### Scenario: 切换组织
- **WHEN** 当前 organizationId 发生变化
- **THEN** 客户端先从界面移除旧组织日历数据，再加载新组织对应缓存和云端数据

#### Scenario: 登出
- **WHEN** 当前成员登出
- **THEN** 客户端停止同步、隐藏所有受保护日历内容且不向未登录界面暴露缓存

#### Scenario: 旧请求延迟返回
- **WHEN** 身份切换后旧分区的网络请求才返回
- **THEN** 客户端丢弃其界面更新效果且不得写入新分区

### Requirement: 云端响应协调本地实体
客户端 SHALL 仅使用云端成功响应更新已保存 Calendar 和 CalendarEvent 的权威字段、版本与删除状态，并按稳定 ID 协调同一分区内实体。

#### Scenario: 创建成功
- **WHEN** 云端确认创建并返回稳定 ID 和版本
- **THEN** 客户端以返回资源写入当前分区且不保留重复的已保存实体

#### Scenario: 更新响应包含规范化字段
- **WHEN** 云端成功响应中的字段值与提交值经规范化后不同
- **THEN** 客户端以云端响应覆盖已保存实体并展示权威值

#### Scenario: 写入失败
- **WHEN** 云端拒绝或未确认写入
- **THEN** 客户端不修改缓存中的已保存权威版本和业务字段

### Requirement: 范围缓存记录明确覆盖边界
客户端 SHALL 按租户分区和 Calendar 筛选记录已成功同步的查询范围、排他结束边界与获取状态，不得仅凭部分日程实体推断整个范围完整。

#### Scenario: 月范围加载成功
- **WHEN** 客户端成功获取某月排他范围内所选 Calendar 的完整结果
- **THEN** 客户端记录该范围和筛选组合已覆盖并缓存返回实体

#### Scenario: 范围加载失败
- **WHEN** 月范围请求失败或只返回未完成分页
- **THEN** 客户端不得将该范围标记为完整覆盖

#### Scenario: 查询未缓存相邻月份
- **WHEN** 成员导航到不在已覆盖范围内的月份且在线
- **THEN** 客户端请求缺失范围而不是将无缓存误表示为无日程

### Requirement: 在线刷新结合范围基线与变更游标
客户端 SHALL 在在线时为所需范围建立权威基线并持续使用当前租户分区的后继游标拉取变更；应用变更后保存实体和游标的位置必须保持一致。

#### Scenario: 首次在线同步
- **WHEN** 当前分区没有可用基线或游标
- **THEN** 客户端获取所需范围及 Calendar 基线，并从服务端提供的位置开始后续增量刷新

#### Scenario: 拉取增量更新
- **WHEN** 当前分区存在有效游标且云端返回新增、更新和删除变更
- **THEN** 客户端按顺序应用变更并仅在成功应用后推进到返回的后继游标

#### Scenario: 应用变更中断
- **WHEN** 客户端无法完整持久化一页变更
- **THEN** 客户端不得仅推进游标，并在重试后仍能得到一致结果

#### Scenario: 游标需要重建基线
- **WHEN** 云端表示游标无效或已过期且要求重新基线同步
- **THEN** 客户端使当前覆盖完整性失效、重新获取所需基线，并在成功前不宣称数据已更新

### Requirement: 增量变更按版本防止状态倒退
客户端 SHALL 对同一稳定 ID 仅应用版本高于当前缓存版本的云端变更，并将删除版本作为可比较的权威状态。

#### Scenario: 收到较新更新
- **WHEN** 变更中的资源版本高于缓存版本
- **THEN** 客户端应用该变更并保存新版本

#### Scenario: 收到重复或较旧变更
- **WHEN** 变更版本不高于缓存中的资源或删除版本
- **THEN** 客户端忽略其状态修改效果且仍可安全继续同步

#### Scenario: 删除后收到旧更新
- **WHEN** 已缓存较高删除版本后收到较低版本的资源更新
- **THEN** 客户端保持资源已删除且不令其重新出现在活动视图

### Requirement: 软删除变更清除活动索引
客户端 SHALL 在收到 Calendar 或 CalendarEvent 删除变更时从活动查询、搜索、筛选和范围索引移除资源，同时保留防止旧版本复活所需的删除标记。

#### Scenario: 日程删除变更
- **WHEN** 客户端应用 CalendarEvent 删除变更
- **THEN** 该日程从月视图和议程的活动结果移除且删除版本被保留

#### Scenario: 日历删除变更
- **WHEN** 客户端应用 Calendar 删除变更
- **THEN** 该日历退出筛选列表且其日程不再作为活动结果显示

### Requirement: 跨设备写入通过刷新收敛
客户端 SHALL 在页面进入前台、网络恢复、成功本地写入及合理的在线刷新触发点检查云端变更，使其他设备已提交的数据无需 Agent 即可收敛到当前视图。

#### Scenario: 页面重新进入前台
- **WHEN** 日历页面从后台恢复且网络可用
- **THEN** 客户端从当前游标刷新变更并更新可见结果

#### Scenario: 网络恢复
- **WHEN** 客户端从离线恢复在线
- **THEN** 客户端先刷新云端权威变更，再允许成员基于最新版本提交已打开的编辑

#### Scenario: 本地写入成功
- **WHEN** 当前客户端的日程写入获得云端成功响应
- **THEN** 客户端协调该响应并安排游标刷新以收敛相关云端变更

### Requirement: 离线模式只读展示已缓存覆盖
客户端 SHALL 在离线时仅展示当前租户分区中已缓存的数据，并明确标识离线状态、缓存覆盖边界和可能过期的数据；不得发起或排队权威日历写入。

#### Scenario: 离线查看已缓存月份
- **WHEN** 成员离线打开当前分区中已完整缓存的月份
- **THEN** 客户端显示缓存日程并明确标识为离线且可能不是最新状态

#### Scenario: 离线查看未缓存月份
- **WHEN** 成员离线导航到未完整缓存的月份
- **THEN** 客户端显示数据不可用或不完整状态且不得将空结果表示为确定无日程

#### Scenario: 离线尝试删除
- **WHEN** 成员离线尝试删除 Calendar 或 CalendarEvent
- **THEN** 客户端阻止权威删除且不从已保存缓存中永久移除资源

#### Scenario: 离线尝试保存
- **WHEN** 成员离线提交创建或编辑表单
- **THEN** 客户端不发送、不排队该写入并仅允许将输入保留为本地草稿

### Requirement: 草稿与已保存资源严格区分
客户端 SHALL 将未提交表单草稿作为当前租户分区内的本地非权威数据保存，明确标记未同步，且不得把草稿加入云端日程结果、游标或版本状态。

#### Scenario: 保存离线草稿
- **WHEN** 成员离线编辑日程表单并选择保留草稿
- **THEN** 客户端在当前分区保存草稿并明确显示其尚未提交到云端

#### Scenario: 恢复草稿
- **WHEN** 同一 deployment、organization 和 member 再次打开对应创建或编辑流程
- **THEN** 客户端可恢复草稿内容但不将其表示为已保存 CalendarEvent

#### Scenario: 其他成员登录
- **WHEN** 另一 member 使用同一 Desktop 安装登录
- **THEN** 客户端不显示、不提交且不删除前一 member 的草稿

#### Scenario: 上线后提交草稿
- **WHEN** 原成员恢复在线并明确提交仍有效的草稿
- **THEN** 客户端先使用最新云端资源版本校验提交，并仅在成功响应后清除草稿和显示已保存状态

### Requirement: 编辑中的云端冲突不得静默覆盖
客户端 SHALL 在草稿或未提交编辑所基于的资源版本落后于云端时保留用户输入并要求显式解决，不得以本地内容静默覆盖云端状态。

#### Scenario: 编辑期间收到远端更新
- **WHEN** 客户端收到高于表单基准版本的同一 CalendarEvent 更新
- **THEN** 客户端保留表单输入并标记底层资源已变化，且不自动提交覆盖

#### Scenario: 编辑期间收到远端删除
- **WHEN** 客户端收到当前编辑 CalendarEvent 的删除变更
- **THEN** 客户端保留可恢复的输入并明确说明原资源已删除，不将其继续表示为可直接更新的活动资源

### Requirement: 缓存不扩大服务端授权
客户端缓存 SHALL 仅用于体验优化；所有在线写入和需要云端确认的读取仍必须接受服务端授权，缓存命中不得被视为成员持续拥有资源访问权的证据。

#### Scenario: 成员资格被撤销
- **WHEN** 云端拒绝刷新因为成员不再属于当前 organization
- **THEN** 客户端停止展示和同步该分区的受保护数据且不允许从缓存继续操作

#### Scenario: 缓存中存在其他资源 ID
- **WHEN** 缓存因历史状态含有当前成员不再有权访问的资源 ID
- **THEN** 客户端不得使用该 ID 绕过云端授权读取或写入资源

### Requirement: 缓存生命周期可控且不跨身份泄漏
客户端 SHALL 支持按租户分区使缓存和草稿失效或清除，并确保日志、遥测和错误信息不包含其他分区的日历业务内容。

#### Scenario: 清除当前身份数据
- **WHEN** 产品策略或成员操作要求清除当前日历本地数据
- **THEN** 客户端仅清除目标 deployment、organization 和 member 分区的缓存、游标及草稿

#### Scenario: 同步错误记录
- **WHEN** 客户端记录同步或缓存错误
- **THEN** 记录可包含诊断标识和错误类别，但不得包含其他租户的标题、描述或草稿内容

### Requirement: 本阶段不提供离线写入同步队列
客户端 SHALL 不创建后台离线写入队列，也不得自动把草稿解释为待同步操作；团队共享、重复规则、提醒、会议、任务叠加和外部日历同步的缓存语义留给后续阶段。

#### Scenario: 从离线恢复在线
- **WHEN** 客户端包含本地草稿并恢复在线
- **THEN** 客户端刷新权威数据并等待成员显式提交草稿，不自动创建、修改或删除云端资源
