---
title: "Workflows"
description: "Use chat and session groups to keep JuggleWork organized."
---

Workflows are how you turn normal JuggleWork chats into organized, repeatable work. In the UI, every session can be renamed, pinned, archived, reordered, or moved into a custom group folder from the session menu. Group folders are workspace-specific: create a group like `Research`, `Ready for review`, `Shipped`, or `Bugs`, then move sessions into that group as the work changes.

You can also describe the workflow in the composer while you work. For example: `When this is done, rename the session to "Auth cleanup", move it to Ready for review, and pin it`, or `If this turns into a bug investigation, put it in Bugs; otherwise archive it when finished.` Those instructions map to JuggleWork's session management primitives: `rename` changes the session title, `move to group` stores a session-to-group assignment, `pin` keeps important sessions at the top, `archive` hides finished sessions without deleting them, and manual ordering lets you arrange sessions and groups around your process.

This makes session organization dynamic instead of manual bookkeeping. A team can keep groups for `Triage`, `In progress`, `Needs human review`, and `Done`, then ask JuggleWork in chat to classify future sessions into those buckets as work completes. The exact groups and actions are configurable from the UI, so the workflow can match how you already work instead of forcing a fixed project-management structure.

## Next prompt suggestions

Turn on **Settings → General → Next prompt suggestions** to see a short, gray suggestion for your next message. This setting is **off by default**. Suggestions use the current session model for an extra request and may incur additional model charges.

- Suggestions are attempted only after a newly observed turn succeeds in the active, visible workspace chat. The composer must be completely empty, including attachments and references, with no queued follow-up both at the initial trigger and immediately before the request is dispatched. If either check fails, clearing the draft later does not generate a suggestion for that turn. Historical turns are not backfilled, and a suggestion is not guaranteed after every reply.
- Suggestions appear only as gray placeholder text in a completely empty composer, without a separate row below the editor or a visible Tab hint. Any text, including spaces or newlines, pasted content, attachments, mentions, chips, or Office references hides the suggestion. Clearing all input restores the same suggestion. Ordinary editing after dispatch keeps the pending request or ready result; a result never overwrites your draft and stays hidden while the composer is nonempty.
- Press **Tab** in the editor to accept a suggestion only when both the actual editor and the complete composer are empty. It becomes an editable draft with the caret at the end. A nonempty composer keeps its normal Tab behavior and existing text, selection, chips, attachments, and references. Acceptance is one undoable edit: **Undo** or clearing the draft restores the original suggestion; **Redo** hides it again because the draft is nonempty. This does **not** send it, queue work, or grant authorization; review or edit it, then send normally. Input methods and open menus keep keyboard priority.
- Press **Esc** when no menu or input method composition is active to hide a ready suggestion in the current view without deleting it or changing your draft. Reopening the session or clearing the input can restore it. Turning the setting off, temporary model, readiness, or policy changes, queued work, submission preparation, hidden panes, or page visibility changes also hide ready suggestions without deleting them; they can reappear when the conditions are restored and the composer is empty.
- Generated suggestions are kept in **localStorage**, separately from drafts, and can survive session switches, remounts, and app restarts. They are isolated by server endpoint, workspace, session, and stable account/organization identity; switching back can restore that identity's suggestion. Storage contains only the short suggestion, turn and scope identifiers, and timestamps—not credentials, tokens, full conversation history, or policy snapshots. If storage is unavailable or a read/write fails, suggestions fall back to memory and restart recovery is not guaranteed. The 128-scope limit applies only to memory; it does not evict saved suggestions from disk. There is no multi-window synchronization requirement.
- Only a newer real user turn or deleting the session clears the old suggestion. A new turn replaces the old content as soon as it starts, even if suggestions are off or the next request fails. Reverting or replaying history does not count as a new turn. Session deletion clears all account/organization identities for that endpoint, workspace, and session, through both the `session.deleted` event and direct cleanup after a successful deletion.
- Each turn has at most one suggestion request, with no automatic regeneration. **Pending requests are not persisted**: Esc, sending or preparing a submission, queuing a follow-up, a new turn, account/organization, policy, model, session, workspace, readiness, visibility, or setting changes, and unmounting can cancel them. Late results are ignored, and cancelled, empty, failed, or skipped requests are not retried for that turn, including after restart. Restoring an existing suggestion through Undo, clearing, reopening, or re-enabling the setting does not call the model; old turns without a saved result are not backfilled.

Supported models use directly resolvable credentials with **OpenAI-compatible Chat Completions**, **OpenAI Responses**, or **Anthropic Messages**. Each generation uses the current session model through its workspace server, with no tools, no streaming, at most 512 output tokens, and a single 8-second server budget covering history reads, model resolution, inference, response reading, and revalidation. Suggestions must be a single paragraph of at most 240 UTF-16 code units. OAuth-only models and models requiring a separate reasoning budget are skipped, without switching models or providers. Older remote servers without the suggestion capability are also skipped, without falling back to the local server. If the completed turn's user message contains Office selections or cloud document references, that turn is skipped because its context is not supported; adding references to your next draft after dispatch hides the suggestion without cancelling it. Unavailable context, unsupported models, or generation failures simply leave the normal composer in place.
